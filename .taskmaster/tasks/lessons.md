# Уроки

## Импорт обязан сохранять исходные timestamp'ы, не полагаться на DEFAULT (2026-09-10)

**Ошибка:** `bulk_import_leads()` при INSERT новых заявок из файла Tilda не
заполнял `leads.created_at` → срабатывал `DEFAULT CURRENT_TIMESTAMP` → у всех
импортных строк дата регистрации = момент импорта. Незаметно ~полгода, пока
не полезли смотреть чарт динамики регистраций в DataLens: у Жары-2026 все
~3500 заявок «зарегистрированы» в августе (реконсиляция стартового списка),
кривая роста регистраций сломана на 3 чартах сразу (Д1/Д1%/Д2).

**Почему не заметили раньше:** 2024–2025 данные пришли через вебхук в
реальном времени — там `DEFAULT CURRENT_TIMESTAMP` даёт верную дату. Порча
только у пути, где событие произошло в прошлом, а строка создаётся сейчас.

**Правило:**
- Любой импорт/бэкфилл/миграция, создающая строки задним числом, ДОЛЖНА
  переносить исходные временны́е метки из источника. `DEFAULT
  CURRENT_TIMESTAMP` / `NOW()` корректны ТОЛЬКО для realtime-путей (вебхук,
  живой ввод).
- Перед тем как игнорировать колонку источника («в нашей таблице для неё нет
  поля») — проверить, не понадобится ли она аналитике/отчётности. Колонку
  `Date` выгрузки Tilda годами держали в `_KNOWN_IGNORED_HEADERS`.
- При UPDATE существующих строк дату двигать только НАЗАД (`LEAST(col, new)`)
  — не затирать более раннюю реальную метку из другого источника.

**Диагностический приём:** распределение по месяцам (`GROUP BY
DATE_FORMAT(col,'%Y-%m')`) сразу показывает «всё в одном месяце» = дата
проставлена пачкой, а не по событию.

## «Localhost не работает» может быть несколько независимых причин сразу (2026-09-11)

**Ситуация:** попросили «почини localhost». Нашлось три независимые причины,
каждая маскировала следующую — чинить по одной, не останавливаться на первой
правдоподобной:

1. SSH-туннель к БД (`dev.ps1`) технически рабочий, просто не был поднят в
   момент проверки — но даже поднятый, он бил напрямую в **прод**-MySQL:
   любой локальный тест на запись реально менял боевые данные. Формально
   "не сломано", но не решает настоящую цель ("не лить изменения в прод").
2. `config/maintenance_mode.local` (гитигнор-файл) отсутствовал на машине.
   Дефолт "файла нет → maintenance ON" — весь публичный API отдавал 503,
   **независимо от БД**. Один такой middleware-флаг замаскировал бы под
   собой вообще любой другой фикс, если бы его не поймали.
3. Мелкий race Redis/WSL2 на холодном старте — Linux-процесс слушает раньше,
   чем Windows успевает поднять localhost-проброс порта.

**Правило:**
- На "у меня не работает локально" не чинить первую найденную причину и
  считать готовым — прогнать реальный сквозный тест (в этом случае —
  `pytest tests/integration/`, не только unit) и смотреть, сколько ещё
  падает и почему, пока падения не станут явно "не отсюда" (чужой баг теста,
  устаревший эндпоинт).
- Отличать "починили механизм" от "решили исходную цель пользователя".
  Туннель к БД был рабочий с июня — но не решал "не трогать прод", ради
  чего чинили. Задавать себе вопрос "а зачем это вообще нужно было" не
  только на старте, но и когда первый найденный баг уже исправлен.
- `*.local`-конфиг-флаги с "файла нет → включено" дефолтом (maintenance,
  history) незаметно для локальной разработки: на VPS файл давно создан
  и забыт, на свежем чекауте — нет. Стоит документировать такие файлы явно
  (например, в `.env.local.example`/README), а не только в docstring
  функции-геттера.

## Переименование по grep не ловит значения, собранные динамически из API (2026-09-15)

**Ошибка:** переименовал «Х Трейл» → «Забег Икс» везде, что нашёл через
`grep -i "Х Трейл"` по репозиторию (шаблоны, JS-таблицы названий). Трекер
конкретно этого события всё равно показывал старое название — заголовок
собирается в браузере из ответа `/api/current-event` (`cfg.name`), никакого
текста «Х Трейл» в файлах не существует, grep физически не мог это найти.

**Правило:**
- После переименования сущности, у которой есть API-driven отображение
  (заголовки/статусы, собранные JS из ответа сервера, а не захардкоженные
  в HTML/шаблоне) — не полагаться на текстовый поиск как на полное
  покрытие. Нужно живой рендер конкретно этой сущности (открыть страницу/
  прогнать сценарий), не только грепнуть исходники
- Заодно вскрылось: одно поле конфига (`name`) годами обслуживало и показ
  пользователю, и ключ для запросов к БД — молча совпадало для всех
  событий, пока не завели случай с расхождением. См.
  `knowledge/debugging/display-name-vs-db-event-name-conflated-field.md`
  (Obsidian) — при добавлении новой сущности с «человекочитаемым текстом» и
  «машинным ключом» заводить два явно разных поля сразу, даже если сейчас
  значения совпадают.

## Внешние бесплатные зависимости (CDN/tile-провайдеры) могут тихо поменять политику (2026-09-15)

**Ошибка:** карта трекера годами использовала `basemaps.cartocdn.com`
(CartoDB) без ключа — рабочий бесплатный сервис внезапно (без изменений в
нашем коде) стал требовать API-ключ и отдавать водяной знак вместо тайлов
на ВСЕХ страницах сайта одновременно.

**Правило:** если внешний сервис (карта, шрифты, аналитика) выглядит
"сломанным одинаково везде и сразу" без недавнего деплоя — в первую очередь
проверить сам сервис напрямую (`curl` к его URL), не искать баг в своём
коде. Бесплатные сторонние API могут менять условия без предупреждения;
при выборе такого провайдера для продакшена — предпочитать вариант без
скрытых ограничений (лицензия/квота/ключ), а не самый похожий по стилю.

## Схема БД может сделать «мягкое» решение по данным невозможным — проверять ДО согласования (2026-09-23)

**Ошибка:** при импорте исторических заявок согласовал с пользователем
вариант «Детский забег за старые годы импортируем без разбивки по
дистанции» — звучало как самый честный вариант (не выдумывать данные).
На прогоне выяснилось: `events.event_distance` — `DECIMAL NOT NULL`, а
триггер `trg_leads_before_insert` обязан распарсить из текста
`leads.event_distance` реальное число, иначе не создаст строку `events` и
весь INSERT падает. Пришлось возвращаться к пользователю и переигрывать
решение на эвристику по возрасту.

**Правило:** прежде чем предлагать пользователю варианты обработки данных
(«оставим пустым», «поставим заглушку», «не будем заполнять»), проверить
схему и триггеры на NOT NULL / тип / парсинг. Вариант, который нельзя
записать в БД, — не вариант, и согласовывать его значит тратить круг
переписки впустую.

## Триггеры, рассчитанные на realtime, врут при импорте задним числом (2026-09-23)

**Ошибка:** `trg_leads_after_insert` ставит `clients.first_lead_date`
только при ПЕРВОЙ заявке клиента и никогда не двигает её назад — для
realtime это верно (каждая следующая заявка позже). При импорте
исторических данных строки идут не хронологически, и у клиента с заявкой
2020 года, вставленной раньше заявки 2016 года, `first_lead_date` осталась
2020-й.

**Правило:** после любого импорта задним числом — пересчитывать
производные поля (`MIN`/`MAX`-агрегаты, «первый/последний раз»), а не
полагаться на инкрементальные триггеры. Инкрементальные счётчики
(`count_leads`, `total_amount` через `+=`) от порядка не зависят и
пересчёта не требуют — проверять нужно именно «первый/последний».

## Батч-скрипту не нужен пул соединений (2026-09-23)

**Ошибка:** одноразовый импорт использовал `get_pooled_connection()`
приложения. На проде `max_connections=20`, из них ~17 постоянно держит
само приложение (3 воркера × `pool_size=10`); пул скрипта попытался
открыть ещё 10 и упал с `1040 Too many connections`.

**Правило:** скрипты в `scripts/` и `deploy/` — одно прямое
`mysql.connector.connect()`, а не пул приложения. Заодно: если у прода
`max_connections` меньше, чем `воркеры × pool_size`, приложение способно
упереться в лимит само по себе — стоит сверять эти числа.

## Часовой пояс источника устанавливать сверкой с известными часами, а не эвристикой (2026-09-24)

**Ошибка:** для Ночного забега 2025 я определил пояс колонки «Дата оплаты» в
выгрузке Tilda по суточному ритму регистраций (в какие часы провал) и решил,
что это UTC. Импорт записал 680 дат на 3 часа позже реальных. Ошибку нашёл
уже при следующей задаче: сверил выгрузку с заявками вебхука, у которых
`created_at` — серверное время получения. Разница оказалась ровно −3.0 ч у
сотен строк, то есть «Дата оплаты» по Москве. Шесть часов окна эвристики не
различают UTC и MSK.

**Правило:**
- Пояс любой колонки времени во внешнем источнике определять точным
  сопоставлением тех же событий с источником, у которого пояс известен
  (вебхук, серверный `NOW()`), и смотреть распределение разницы (должен быть
  один пик с точностью до минут). Эвристика «ночной провал» — только для
  подсказки
- Наивное время пишется в TIMESTAMP-колонку в поясе сессии MySQL. Скрипты,
  которые пишут время, должны явно задавать `SET time_zone`, а не
  полагаться на пояс сервера или локальной машины (прод и локальная БД
  здесь различались: MSK против Красноярска)
- Проект живёт по красноярскому времени (Asia/Krasnoyarsk, +07:00): сервер,
  MySQL, пул соединений, фронт (`timeZone: 'Asia/Krasnoyarsk'`)
