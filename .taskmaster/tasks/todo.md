## Как сейчас (инвентаризация прода)
- VPS: `Europe/Moscow`. MySQL: `time_zone=SYSTEM`, то есть MSK; таблиц часовых поясов нет. Python `datetime.now()`, `NOW()` и логи идут по MSK
- В БД `TIMESTAMP`: `leads.created_at`, `age_group_configs.created_at`, `participant_photos.created_at`. Хранятся в UTC, при чтении показываются в поясе сессии, то есть по MSK. `DATETIME`: `clients.first_lead_date`/`last_lead_date` — это копии, записанные по MSK
- DataLens (пользователь `km_analytic`) видит время в поясе сервера, то есть по MSK
- Фронт: `toLocaleTimeString()` без `timeZone` в tracker-map (время старта, прогноз финиша), tracker-api, admin-monitoring, duathlon-chart — время показывается по часам браузера зрителя
- `gun_time` в YAML уже явно задан по Красноярску (`results_service`: `timezone(timedelta(hours=7))`)
- cron и systemd-таймеры на VPS только системные (certbot, apt, sysstat), у приложения таймеров нет
- Импорты со сдвигом:
  - Жара 2023–2024: `sent` в UTC записан как MSK, реальное время на 3 ч позже
  - «Бум» 2020–2022: `Payment date` в UTC записан как MSK, на 3 ч позже
  - «Бум» 2013–2022, заглушки 01.01 00:00 MSK: должны стать 01.01 00:00 по Красноярску
  - Жара 2026 и Детский 2026 из админки: колонка `Date` CRM-выгрузки, по данным Ночного 2025 это UTC−10. Проверить на исходных CSV

  2022») — опечатка. ✅ **Пользователь решил: считать `1991`**

### 4. Фамилия/Имя — 63 строки, где `surname == name` (не 50, как думал изначально)

Первый проход искал только многословные фамилии (59→50 после проверки);
расширенная проверка (`surname.lower() == name.lower()`, без требования
пробела) нашла ещё 13 однословных случаев той же природы. Итого 63 строки,
**3 разных случая** — разложены по 3 листам файла
`Бум_разбор_ФИО.xlsx` (отправлен пользователю в Downloads):

- ✅ **Лист 1 (50 строк)** — пользователь прислал разбор Фамилия/Имя для
  всех 50 строк (`Бум_разбор_ФИО.xlsx`, лист «1. ФИО задвоено», колонки J/K)
- ✅ **Лист 2 (5 строк)** — **удалить**, не импортировать (surname/name —
  обязательные поля в БД, оставлять половину неизвестной нельзя)
- ✅ **Лист 3 (8 строк)** — пользователь решил: **удалить все 8**, включая
  5 строк `1/1` с реальными email/телефоном (не пытаемся восстановить имя)

Есть и настоящие многословные фамилии БЕЗ бага — не в списке (например
`ДИАС ДЕ КИХАНО БАРБЕРО` / `ДАНИЭЛЬ`, испанская составная фамилия +
отдельное имя, `surname != name`) — их трогать не нужно.

### 5. Явные дубли внутри самого файла

86 уникальных комбинаций (surname+name+birthday+product) встречаются 2-3
раза подряд — 88 «лишних» строк. Похоже на случайно продублированные при
склейке экспортов строки. Нужно дедуплицировать перед импортом (оставить
одну копию).

### 6. Email / телефон — по мелочи, не блокирует

- 747 строк без email, 2 строки с явным мусором вместо email (`"ему 49
  лет - группа 40-49"`, ссылка на vk.com) — на пустое/мусорное подставить
  сентинел `example@mail.ru`, как уже делает `bulk_import_leads()`
- 157 строк без телефона — оставить пустым
- Телефон в основном 11 цифр (формат `7XXXXXXXXXX`) — 17 строк с другой
  длиной (7/9/10/12 цифр) — не блокирует импорт, но не помешает проверить руками

### 7. Пол — тривиальная нормализация

`'Мужчина '`/`'Женщина '` (7+5 строк, хвостовой пробел), `'Женский'` (1
строка, другое слово) → `.strip()` + маппинг на `Мужчина`/`Женщина`.

### 8. `Payment date` → `leads.created_at` — КРИТИЧНО, чтобы не повторить недавний баг

Ровно тот класс проблемы, что чинили 2026-09-10 (см.
`.taskmaster/tasks/lessons.md` — «Импорт обязан сохранять исходные
timestamp'ы»): если не прокинуть `Payment date` в `created_at`, все 21000
исторических записей получат `created_at = момент импорта` и снова
сломают чарты динамики регистраций в DataLens, теперь для 10 лет данных
разом. Формат в основном текстовый ISO (`'2020-08-01 08:43'`, легко
парсится), но 16 строк — сырое число Excel (float/int serial date),
нужна отдельная конвертация.
