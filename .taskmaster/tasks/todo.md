**Проект:** Красмарафон

## Диагноз (подтверждён данными)

### Корневая причина — не оформление чартов, а данные

Чарты **Д1 (Нарастающий итог)**, **Д1% (Нарастающий итог, %)**, **Д2 (Регистрации
за период)** строят ось X по `time_bucket`, который считается из
`days_before_event = DATEDIFF(e.event_date, DATE(l.created_at))` (SQL датасета
`km_leads`).

`leads.created_at` у **импортированных** через файл Tilda заявок = момент
импорта, а НЕ реальная дата регистрации:

```
SELECT DATE(created_at), COUNT(*) FROM leads WHERE event_name='Жара' AND event_year=2026 ...
2026-08-14 → 2629
2026-08-17 → 102
2026-08-18 → 571
2026-08-19 → 129
2026-08-21 → 4
2026-08-22 → 73
```
Гонка была 23.08.2026 → все заявки валятся в корзины «09. 1 нед.» и
«10. Посл. нед.», корзины 01–08 пустые. У 2025 (данные пришли вебхуком)
кривая нормальная: 137 → 321 → … → 1166.

**Причина в коде:** `bulk_import_leads()`
([src/analytics/db_results.py:1877](../../src/analytics/db_results.py#L1877))
при INSERT новых заявок НЕ заполняет `created_at` → срабатывает
`DEFAULT CURRENT_TIMESTAMP`. Реальная дата регистрации ЕСТЬ в файле Tilda —
колонка `Date`, но парсер её выбрасывает
([tilda_import_parser.py:138](../../src/krasmarafon/services/tilda_import_parser.py#L138),
`_KNOWN_IGNORED_HEADERS`). Вебхук
([webhook.py:73](../../src/krasmarafon/routers/webhook.py#L73)) тоже полагается
на DEFAULT — но там это корректно (реальное время получения).

### Вторичное — в Д1% нет линии 2025

Д1% отвязан от селектора «Год» (Связи: Год ↔ Д1% = «Не связаны») — должен
показывать 2025 и 2026 вместе. Формула %-меры делит на `total_leads_per_event`
(не на `slot_limit`), т.е. пустой `slot_limit` у Жары-2025 (`events.slot_limit`
NULL для 2024/2025/2027) — НЕ причина. Причина не установлена — нужна доп.
диагностика (см. блок «Открытые вопросы»). Д1 те же строки 2025 показывает
нормально.

### `events.slot_limit`
NULL у Жары 2024/2025/2027; заполнен только 2026 (700/1550/2050 по дистанциям).
Влияет на **Д4 (Остаток слотов)** и **Д3 (%Продаж)** для прошлых лет, если их
там смотрят. Формулу Д1% не трогает.

### Колонка `Date` в файле Tilda — проверена (2026-09-10)
Файл `leads-35d2f32...csv` (Жара 2026, 2834 строки):
- `Date` = **реальное время подачи заявки**, формат `YYYY-MM-DD HH:MM:SS` (ISO,
  19 симв.), **заполнена на 100%**, диапазон 2025-08-24 … 2026-08-19
- Распределение по месяцам — нормальная органическая кривая:
  `2025-08:208, 09:57, 10:28, 11:34, 12:26, 2026-01:61, 02:57, 03:88, 04:93,
  05:243, 06:388, 07:739, 08:812` — именно это должно быть на Д1/Д1%/Д2
- Есть и `Дата оплаты` (idx 32) — время оплаты, на ~минуты-часы позже подачи.
  Берём **`Date`** (подача = момент регистрации)
- Новые колонки, которых парсер ещё не знает: `Дата оплаты`, `Местоположение`
  (idx 32, 33) — сейчас попадут в `unknown_headers`; добавить в
  `_KNOWN_IGNORED_HEADERS` (или `Дата оплаты` — тоже полезна?)

### ⚠️ Файл ≠ БД по числу строк
Файл: 2834 строки. БД (`event_name='Жара' AND event_year=2026`): ≥3500
(из запроса `DATE(created_at)`). БД содержит ≥600 заявок Жары-2026, которых
нет в этом экспорте (дубли? удалённые из Tilda? ручные?). **Переимпорт файла
через `/admin` их удалит** (реконсиляция «файл — источник истины»). →
бэкфилл делаем **отдельным скриптом (только UPDATE, без DELETE)**.

### event_id / client_id — ОК
Триггер БД `trg_leads_before_insert` резолвит оба (по event_name+distance+year).
Проверено: `event_name='Жара' AND event_year=2026` → 3508 строк, `event_id=0`: 0,
`client_id=0`: 0, `is_duplicate=1`: 0. JOIN `events` в датасете работает.

### `leads.created_at` — определение (проверено 2026-09-10)
`timestamp NOT NULL DEFAULT CURRENT_TIMESTAMP`, EXTRA = `DEFAULT_GENERATED`
(**без `ON UPDATE CURRENT_TIMESTAMP`**). Значит:
- порча только от INSERT (новая строка → default = момент импорта)
- существующие UPDATE в `bulk_import_leads()` дату НЕ трогают — можно спокойно
  добавить `created_at = LEAST(...)` только туда, где нужно
- колонка NOT NULL → INSERT всегда передаёт значение явно

### Файл 2834 vs БД 3508 — норма
674 «лишних» в БД — регистрации после даты экспорта (max `Date` в файле —
2026-08-19, гонка 23.08) + ручные. Их `created_at` ≈ реальной поздней
регистрации. Скрипт бэкфилла обновит что сматчит, остальное — отчётом.
