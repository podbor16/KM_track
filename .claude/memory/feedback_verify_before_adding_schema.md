Перед тем как добавлять новое поле в БД (миграцию) из соображений "нельзя менять семантику существующего поля", нужно реально проверить код (grep все использования), а не полагаться на прошлую документацию/архитектурную заметку.

**Инцидент:** при добавлении пола участников эстафеты Siberman сначала завели отдельное поле `member_gender` + миграцию, решив, что `gender='E'` — рабочий маркер формата для ranking/фильтрации (со ссылкой на старую архитектурную заметку). Пользователь усомнился ("давай подумаем над этим") — grep по коду показал, что `gender='E'` нигде реально не используется: и ranking (`service.py`), и SQL-выборки (`db.py`) уже разделяют личник/эстафету по полю `format`, не по `gender`. В итоге миграцию откатили (благо не успели применить на сервере), поле убрали, эстафета хранит реальный пол прямо в `gender`.

**Why:** архитектурные заметки/докстроки могут описывать историческое обоснование, которое перестало быть актуальным (или было ошибочным с самого начала) — единственный источник истины — фактическое использование поля в коде.
**How to apply:** прежде чем предлагать новое поле/колонку/миграцию "чтобы не сломать существующую логику", сделать `grep` по всем местам использования поля, которое якобы нельзя трогать, и убедиться, что оно правда read где-то критичном. Если пользователь сомневается в решении — это сигнал перепроверить, а не защищать первоначальный вариант.
