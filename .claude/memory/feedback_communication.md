Предпочитает деловой, прямолинейный стиль на русском языке.

**Why:** Быстро принимает решения, не хочет тратить время на лишние объяснения и воду в тексте. Уже зафиксировано в CLAUDE.md проекта ("Отвечать на русском языке"), но было ДВА повторных случая в одной сессии (2026-07-27, диплом Красмарафона): сначала ассистент отвечал на английском ("я просил тебя рассуждать и отвечать на русском"), затем — после того как в память была записана правка про user-facing текст — сорвался именно видимый блок рассуждений/reasoning ("ты опять рассуждаешь на английском"). То есть одной пометки "отвечать по-русски" недостаточно — переключение на английский происходит именно в reasoning-блоке, который тоже виден пользователю.

**How to apply:**
- **АБСОЛЮТНО ВСЁ, что видит пользователь — на русском, без исключений: и сам видимый блок рассуждений (reasoning/thinking), и промежуточные апдейты по ходу работы, и финальное резюме.** Это не только про финальный текст ответа — reasoning-трейсы тоже читает пользователь и тоже ожидает русский язык. Код, CSS-свойства, имена библиотек, командные флаги — нормально оставлять как есть на английском, но связующий текст и рассуждения вокруг них — по-русски.
- Если поймал себя на мысли на английском — переключиться немедленно, не дожидаясь конца блока рассуждений.
- **Это ХРОНИЧЕСКАЯ проблема — третий пойманный случай (2026-08-03, сессия с subagent-driven-development по Siberman live-ranking): длинные reasoning-блоки при сложном многошаговом проектировании (архитектурные решения, разбор кода перед написанием плана) снова полностью съехали на английский, несмотря на то что это правило уже было явно записано в памяти проекта с 2026-07-27.** Дело не в том, что правило не сохранено или сохранено не на весь проект (memory лежит в `.claude/memory/` этого же проекта — она уже per-project и per-session-persistent) — дело в том, что при высокой когнитивной нагрузке (длинные цепочки рассуждений, subagent-оркестрация) это правило неявно "забывается" по ходу". **Практический вывод: при СТАРТЕ любого reasoning-блока явно проверять себя на язык, а не полагаться на "само вспомнится" в разгар сложного проектирования — особенно уязвимы длинные аналитические/архитектурные рассуждения перед написанием плана или диагностикой бага.**

**Четвёртый пойманный случай (2026-08-05, сессия по Copernico live-хронометражу бега Siberman):** после длинной серии tool-calls (чтение схемы БД, миграции, рефакторинг apply_to_db, написание copernico_run.py/тестов) финальное ИТОГОВОЕ резюме пользователю снова ушло на английский — сорвался не reasoning-блок, а именно видимый ответ-саммари в конце длинной цепочки инструментов. Общий паттерн для всех 4 случаев: срыв происходит не в начале задачи, а ПОСЛЕ длинной последовательности действий (много tool calls, сложное многошаговое проектирование/имплементация) — то есть проверка языка нужна не только "в начале reasoning-блока", но и отдельно перед каждым видимым текстом, который идёт ПОСЛЕ долгой серии инструментов, включая финальные резюме.
**Пятый пойманный случай (2026-08-21, сессия по раздельным Copernico-пресетам для Жары/Детского забега):** снова финальное резюме после долгой цепочки (несколько раундов subagent-dispatch с ревью, live-fetch к Copernico API, правки YAML-конфигов, git push/деплой) ушло на английский. Пользователь среагировал коротко: "ты ответил на английском, отвечай всегда на русском" — не стал объяснять заново, ожидает что это уже должно быть усвоено. Паттерн подтверждён в 5-й раз: точка срыва — не начало задачи, а именно ФИНАЛЬНЫЙ видимый текст после длинной серии инструментов/субагентов, когда внимание уже переключилось на "что делать дальше по существу" и проверка языка выпадает как будто неважная деталь.

**Практический вывод (обновлено):** перед отправкой ЛЮБОГО видимого текста, который идёт после серии из 3+ tool calls подряд — короткая самопроверка одним вопросом: "на каком языке я сейчас пишу?" — как отдельный, осознанный шаг, а не понадёжда на инерцию. Особенно после: субагентных циклов ревью, длинных investigation-цепочек (live API, grep/read по многим файлам), git push/deploy watch.

- Давать готовый рабочий код сразу, а не только описание или рекомендации
- Структурировать ответ по вариантам, когда есть выбор — с чёткой дифференциацией между ними
- Использовать markdown-форматирование
- Средний объём: включать нужные детали, но без лишнего многословия
- Добавлять объяснения только для действительно сложных операций
- Диаграммы приветствуются для сложной архитектуры
- Не переспрашивать без необходимости — если есть очевидный путь, сразу идти по нему
