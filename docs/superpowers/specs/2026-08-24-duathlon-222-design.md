## Контекст и решения, принятые с пользователем

- Трекер/карта/GPX — **не нужны**: гонка круговая (аналогично суточной велогонке), точки на карте не имеют смысла для многокруговых этапов.
- На странице результатов, помимо обычных КТ (если организатор их даст), нужны **явные колонки по этапам**: время Бег-1, время Вело, время Бег-2 — отдельно от общего времени.
- Хостинг: тот же домен `live-race.triatleta.ru`, что и суточная гонка — **другой путь** (`/duathlon222`), не отдельный поддомен.
- Формат старта: один массовый старт всей гонки. Дальше — личное непрерывное время: T1 сразу после финиша Бега-1, T2 сразу после финиша Вело. Итоговое время участника = время от общего старта до личного финиша Бега-2. Никакого отдельного гандикапа/масс-старта по этапам (в отличие от bike_day2 в Siberman).
- Copernico-структура (один event с полями для 3 этапов, или три отдельных event/preset) — **не подтверждена**, уточняется у организаторов. Дизайн ниже рассчитан на оба варианта: сама модель хранения (широкие колонки по этапам) не зависит от того, как именно Copernico отдаёт данные — меняется только код загрузчика, извлекающий поля.

## Архитектурный выбор: модель Siberman, а не модель tri_24h

В проекте уже есть два прецедента многосоставных гонок:

1. **tri_24h** (`src/triatleta/`) — одна дисциплина, до 173 одинаковых кругов. Хранение: таблица `laps` (одна строка = один круг), место считается по числу кругов + время.
2. **Siberman** (`src/siberman/`) — несколько РАЗНЫХ дисциплин (заплыв/вело/бег), разные этапы с разными моделями старта. Хранение: широкие колонки по этапам в одной строке участника (`swim_s`, `bike1_s`, `bike2_s`, `run_s` и т.п.), место считается и по этапу, и по сумме.

Дуатлон 222 структурно ближе ко второму случаю: 3 РАЗНЫЕ дисциплины с разной скоростью/природой, финиш = сумма этапов, нужны отдельные колонки по этапам. Поэтому берём модель Siberman (широкие колонки), а не модель "N одинаковых кругов" — она не даёт естественного способа выделить "время именно на вело" отдельно от "времени именно на беге".

Никакой Excel-логики Siberman (парсер, google sheets и т.п.) не переиспользуется — данные идут live из Copernico API, как у tri_24h. Это гибрид: **данные — как у tri_24h (Copernico polling), хранение и колонки результатов — как у Siberman (per-stage wide columns)**.

Изоляция от существующего кода: как и `load_tri_results.py` не трогает `load_race_results.py`, новый модуль не модифицирует ни `src/triatleta/`, ни `src/siberman/`, ни `src/krasmarafon/`.

## База данных `duathlon_222`

Отдельная БД на том же MySQL VPS (по аналогии с `triatleta_24h`).

```sql
CREATE TABLE events (
    id INT AUTO_INCREMENT PRIMARY KEY,
    code VARCHAR(50) UNIQUE NOT NULL,
    name VARCHAR(255) NOT NULL,
    gun_datetime DATETIME NOT NULL       -- UTC, единый массовый старт всей гонки
);

CREATE TABLE participants (
    id INT AUTO_INCREMENT PRIMARY KEY,
    event_id INT NOT NULL,
    start_number INT NOT NULL,
    surname VARCHAR(255) NOT NULL,
    name VARCHAR(255) NOT NULL,
    gender VARCHAR(10),                  -- 'M' / 'F' — единственный зачёт
    status VARCHAR(50),                  -- 'active' / 'finished' / 'dnf' / 'dsq'
    -- Личное непрерывное время каждого этапа, секунды от общего старта.
    -- Заполняются по мере прохождения; NULL — этап ещё не начат/не завершён.
    run1_s INT NULL,                     -- финиш Бег-1 (= элапсед от старта гонки)
    bike_s INT NULL,                     -- финиш Вело (элапсед от старта гонки)
    run2_s INT NULL,                     -- финиш Бег-2 = общий финиш (элапсед от старта гонки)
    UNIQUE KEY uniq_event_bib (event_id, start_number)
);
```

**Время этапа** (для колонок "Бег-1"/"Вело"/"Бег-2" на странице) вычисляется вычитанием, не хранится отдельно:
- Бег-1: `run1_s`
- Вело: `bike_s - run1_s`
- Бег-2: `run2_s - bike_s`
- Общее время: `run2_s`

Это тот же принцип, что уже применяется в `krasmarafon` для времени между КТ (`_build_kt_checkpoints`) и в Siberman для сегментов — не завожу новый механизм, переиспользую известный паттерн вычитания соседних кумулятивных отметок.

**rawStatus vs status** (урок из Siberman, [[project_siberman_live_v2]]): `status` участника — это статус ВСЕЙ гонки (`active`/`finished`/`dnf`/`dsq`), не вывод из наличия `run1_s`/`bike_s` (участник, сошедший на вело, всё ещё имеет `run1_s`, но не имеет `bike_s`/`run2_s` — это не должно читаться как "лидирует на вело"). Финишированность этапа проверяется по факту non-NULL соответствующей колонки, ранжирование и допуск к "лидеру"/месту — по `status`.

Если организатор Copernico даёт ещё и промежуточные КТ внутри этапов (круги на вело/беге) — они не меняют эту таблицу; при необходимости добавляется отдельная generic-таблица `checkpoints` (participant_id, stage, seq, elapsed_s) по аналогии с `laps` у tri_24h, но это не в MVP, пока не подтверждено, что организатор такие данные вообще даёт.

## Copernico — открытый вопрос (Task 0, блокирующий)

**2026-08-25:** пользователь подтвердил рабочее предположение — скорее всего Вариант А (один event). Не окончательно, организаторы ещё не подтвердили точные имена полей; конфиги ниже уже написаны под этот вариант.

Неизвестно, как организатор сконфигурирует хронометраж:

- **Вариант А (один event):** один race_id/preset отдаёт для каждого участника поля вроде `times.official_run1`, `times.official_bike`, `times.official_finish` (или подобные — Copernico Cloud поддерживает мультиспортивные дисциплины с сегментами нативно). Тогда `db_event_id` один, конфиг — один YAML-блок с полями трёх этапов.
- **Вариант Б (три отдельных event/preset):** каждый этап — отдельный Copernico event (как дистанции Жары), участники матчатся по номеру между тремя запросами. Тогда загрузчику нужно опросить 3 preset'а и смёрджить по `start_number`.

Схема БД и страница результатов не зависят от выбора — меняется только код `_fetch_*`/маппинга полей в загрузчике. Решить после консультации с организаторами (аналогично тому, как Task 0 у tri_24h откладывал верификацию полей до реального ответа API).

## Frontend — `live-race.triatleta.ru/duathlon222`

Таблица результатов (одна, без вкладок личный/командный — эстафет нет):

`Место | Участник | Бег-1 | Вело | Бег-2 | Итого | Статус`

- Фильтр по полу (М/Ж), переключатель "Абсолют"/"по полу" — как во всех остальных таблицах результатов проекта.
- DNF/DSQ — внизу списка, не участвуют в ранжировании (тот же принцип rawStatus, что в Siberman).
- Обновление — polling каждые 30 сек (как у tri_24h), SSE не нужен для этого масштаба.
- Прогноз финиша (forecastTime) — не в MVP, можно добавить после того, как заработает базовый live-режим (как это делалось в Siberman отдельным этапом).
