# Прогноз времени на КТ и финиша этапа (Siberman)

**Дата:** 2026-08-06
**Статус:** утверждено, готово к планированию реализации

## Проблема

Во время живой гонки зрителям интересно не только "где участник сейчас", но и "когда он финиширует этап" / "когда дойдёт до следующей КТ" — сейчас это приходится прикидывать в уме по текущей скорости. Два разных места:

1. **Таблица КТ в карточке участника** (`participant.html`) — там уже видно детальную историю по каждой отметке, логично показать там же прогноз на ещё не пройденные.
2. **Списки на вкладках этапов** (`results.html`) — прогноз финиша ЭТОГО этапа нужен для всех участников сразу, не заходя в каждую карточку.

## Формула

Линейная экстраполяция средней скорости с начала этапа — единая для обеих дисциплин и обоих мест использования, без развилок по типу этапа (плавание/вело/бег):

```
прогноз_до_X_s = elapsed_so_far_s × (target_dist_km / dist_so_far_km)
```

где:
- `elapsed_so_far_s` — время с начала этапа до последней достигнутой КТ (то же значение, что уже даёт `stagePos()`/`pos.value` в обоих файлах — для bike_day1 это уже сетевое время без заплыва)
- `dist_so_far_km` — дистанция последней достигнутой КТ (`CHECKPOINT_DIST_KM[dbStage][pos.seq]`)
- `target_dist_km` — дистанция КТ/финиша, для которой считаем прогноз

Формула не требует km/ч или темп/100м как промежуточного шага — это просто пропорция, работает одинаково для всех этапов.

**Новый общий хелпер** в `static/js/siberman-common.js`:

```js
// forecastTime(distSoFarKm, elapsedS, targetDistKm) → секунды (число) или null
function forecastTime(distSoFarKm, elapsedS, targetDistKm) {
    if (!(distSoFarKm > 0) || elapsedS == null) return null;
    return elapsedS * (targetDistKm / distSoFarKm);
}
```

Используется и в `results.html`, и в `participant.html` — единственное место с формулой.

## Пересчёт (важно: НЕ кэшируется)

Прогноз нигде не хранится — вычисляется заново при каждом рендере из **текущего** `pos` (последняя достигнутая КТ участника). Как только участник проходит новую КТ, `pos.seq`/`pos.value` сдвигаются, средняя скорость на входе в формулу автоматически становится актуальной, и все прогнозы (следующая КТ, финиш этапа) пересчитываются сами по себе на следующем рендере — ни `results.html` (поллинг раз в 20с), ни `participant.html` не нуждаются в отдельной логике "обновить прогноз".

## Место 1 — `results.html`, вкладки этапов

Применяется только на 4 вкладках: Плавание / Вело День 1 / Вело День 2 / Бег (не на "Итог 1 дня" / "Итог 2 дней" / "Итоги гонки" / Абсолют).

**Новая колонка «Прогноз финиша»** — между «Скорость»/«Темп» (`cfg.metaLbl`) и «Отметка» (существующая колонка **не убирается и не меняется**, они видны рядом):

```
Место | № | Участник | Время | Скорость | Прогноз финиша | Отметка | [Старт вело-2] | Статус
```

Применяется одинаково к личникам (`buildIndividualStageRow`) и эстафетчикам (`buildRelayStageRow`) — тот же `pos = stagePos(...)`, что уже используется для колонки "Скорость"/"Отметка" в этих функциях.

**Значение:** `~ЧЧ:ММ:СС` (с волной), amber/золотой цвет, тёплый оттенок для обеих тем (в кодовой базе уже есть готовая тема-зависимая пара для похожего "это не обычное значение, а особая пометка" — `#b8860b`/`#e0b23c`, используется для "🏆 Рекорд" — переиспользуем те же HEX-значения ради консистентности палитры, но новым CSS-классом `.forecast-cell`, отдельным от `.stage-record`, чтобы не путать смысл "прогноз" со смыслом "рекорд" при чтении кода).

**Пустая ячейка** (без `—`, без волны — совсем ничего), если:
- участник ещё не начал этап (`pos == null`)
- этап уже пройден целиком (`finished === true`, т.к. реальное время уже есть в колонке "Время")
- статус не `active` (DNF/DSQ/DNS)

`target_dist_km` = `CHECKPOINT_DIST_KM[dbStage][STAGE_MAX_SEQ[dbStage]]` (полная дистанция этапа).

## Место 2 — `participant.html`, таблица КТ (`stageBody`)

Для каждой строки таблицы, где `pending === true` (КТ ещё не достигнута, включая финишную строку):

- колонка **«Общее время»** — вместо `—` показывает `~ЧЧ:ММ:СС`, тем же amber-цветом, что и в results.html
- колонки **«Сплит»** и **«Темп/скорость»** — остаются `—` (прогноз сплита между двумя ещё не пройденными КТ не считаем — не запрошено, добавляет путаницы с "прогноз от старта" vs "прогноз сплита")

`target_dist_km` для каждой строки — дистанция ИМЕННО этой КТ (`CHECKPOINT_DIST_KM[dbStage][seq]` цикла), не только ближайшей — все ещё не пройденные строки таблицы получают свой прогноз одной и той же формулой.

Если `pos == null` (этап ещё не начат вовсе) — прогноза нет нигде в таблице, все строки остаются `—` как сейчас.

## Стилизация

Общий CSS-класс `.forecast-cell` (или аналог) с amber/жёлтым текстом — добавляется в обоих файлах (`results.html`, `participant.html`), т.к. у них раздельные `<style>`-блоки (общего CSS-файла для стилей у сайта нет, только `siberman-common.js` для логики).

## Явно вне рамок

- Прогноз финиша **всей гонки** (через все 4 этапа) — не делаем, только прогноз финиша текущего этапа. Разнородные дисциплины (плавание/вело/бег) делают такую экстраполяцию менее осмысленной, и это отдельная фича при необходимости.
- Прогноз сплита между двумя будущими КТ в карточке участника.
- Кэширование/хранение прогноза где-либо (БД, localStorage) — всегда live-вычисление.

## Тесты

Регрессионные JS-тесты (тот же паттерн `node:vm`, что в `tests/js/test_siberman_results_merge.js` и `tests/js/test_siberman_participant.js`):

- `forecastTime()` — базовый расчёт, `null` при `distSoFarKm <= 0` или `elapsedS == null`
- `results.html`: колонка "Прогноз финиша" показывает `~` + время для активного участника посреди этапа; пустая для финишировавшего; пустая для не начавшего; пустая для DNF
- `participant.html`: будущие строки таблицы КТ показывают прогноз в "Общее время", "Сплит"/"Темп" остаются `—`; после прохождения КТ строка показывает реальное значение (не прогноз)
