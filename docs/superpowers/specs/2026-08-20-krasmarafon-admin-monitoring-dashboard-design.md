# Мониторинг сервера в /admin — дизайн

## Контекст и цель

Нужен онлайн-дашборд состояния сервера прямо в `/admin` — пиковые нагрузки, свободная
память и остальные ключевые показатели, в реальном времени. Плюс push-уведомления на
русском при критической нагрузке с конкретными предложениями по решению.

Backend уже почти полностью существует и активно работает в проде: `MetricsCollector`
(`src/monitoring/collector.py`) каждую минуту (`_metrics_flusher()` в `app.py`) пишет в
SQLite (`data/server_metrics.db`) CPU%, RAM used/total, уникальные IP, запросы,
HTTP-ошибки, среднее время ответа, число SSE-соединений — и считает единый индекс
нагрузки (`load_score` 0-100, вес RAM 40% + время ответа 40% + ошибки 20%) с русской
меткой (Низкая/Умеренная/Высокая/Критическая). При «Высокая»/«Критическая» или
`cpu_percent >= 70` пишет строку в `data/high_load_alerts.csv`; при «Критическая» или
`cpu_percent >= 90` (не чаще раза в 15 минут) шлёт push через ntfy.sh — `NTFY_URL`
реально настроен в проде, уведомления уже уходят, `high_load_alerts.csv` уже содержит
реальные алерты за 18-19.08 (среднее время ответа доходило до 17-18 секунд — те же
эпизоды медленной загрузки, что разбирались отдельно в этой же сессии).

API для дашборда тоже уже готов и защищён `api_require_auth`:
`GET /api/admin/metrics?hours=1|6|24|168|720|2160|4320|8760` (история с даунсэмплингом
по `hours_to_bucket_secs()`) и `GET /api/admin/metrics/live` (SSE, новая точка каждые
5 секунд).

Двух вещей не хватает: (а) визуального отображения всего этого в `/admin` — данные
собираются, но посмотреть их сейчас можно только через SSH/CSV; (б) конкретных
предложений «что делать» в тексте уведомлений — сейчас там только цифры.

**Отдельно, для ясности:** на VPS также работает независимый демон Netdata со своим
web UI (`systemctl is-active netdata` → active) — в этот дизайн не входит, пользователь
явно выбрал развитие своего `MetricsCollector`, не Netdata.

## Объём

- Новая вкладка «Мониторинг» в `/admin`, в конце списка вкладок (после «Трансляции»).
- Живой блок текущего состояния + графики истории (переключатель диапазона, по
  умолчанию 24 часа) + таблица последних алертов с советами.
- Обогащение push-уведомлений ntfy конкретными советами по решению.
- Никаких изменений схемы SQLite/CSV, никаких новых системных зависимостей — Chart.js
  уже используется в проекте и лежит локально (`static/lib/chart4/`).

## Backend

### `generate_suggestions(point: dict, recent_avg_sse: float | None) -> list[str]`

Новая чистая функция в `src/monitoring/collector.py` (без сайд-эффектов, без обращений
к БД/сети — только вычисления над переданными числами, легко тестируется в изоляции).
Принимает точку метрик (тот же dict, что уже строит `flush()`/возвращает `query()`) и
недавнее среднее число SSE-соединений для сравнения (baseline — см. ниже). Возвращает
список готовых русских строк-советов (может быть 0, 1 или несколько сразу, если
проблема многофакторная).

Условия и пороги — из них переиспользуется из уже существующего кода только порог
времени ответа (п.2, тот же `1500` мс, с которого `_load_score()` уже даёт `rt >= 35`
в `_read_ram`/`rt`-шкале). RAM 80%, ошибки 5%, SSE-аномалия — новые пороги, в текущем
коде для них нет одноимённых констант (`_ALERT_CPU_THRESHOLD`/`_EMAIL_CPU_THRESHOLD`
относятся только к CPU, не к RAM/ошибкам/SSE), их предстоит завести как новые
модульные константы в `collector.py` рядом с существующими `_ALERT_*`:

1. **RAM** (`ram_used_mb / ram_total_mb >= 0.8`):
   `"RAM {ram_pct:.0f}% ({ram_used_mb} из {ram_total_mb} MB). ps aux --sort=-%mem | head -5 — какой процесс тянет. Если один gunicorn-воркер сильно больше других — похоже на утечку, сброс: systemctl restart km_track. Если равномерно у всех — это реальный трафик, рассмотреть апгрейд VPS до 4 ГБ."`

2. **Время ответа** (`avg_response_ms >= 1500`, тот же порог, с которого `_load_score()`
   уже даёт `rt >= 35`):
   `"Среднее время ответа {avg_response_ms:.0f} мс. Проверьте, не идёт ли сейчас bulk-импорт заявок в /admin — это тяжёлая синхронная операция. Если нет — возможен «thundering herd» на /api/registered-runners после истечения 5-минутного кеша: много одновременных запросов бьют в «холодную» БД одновременно."`

3. **Ошибки** (`http_errors / total_requests >= 0.05`, если `total_requests > 0`):
   `"Ошибок {err_rate:.0f}% от {total_requests} запросов. journalctl -u km_track --since '15 min ago' | grep -iE \"error|traceback\" — конкретные исключения. systemctl status mysql redis-server — не легла ли база/очереди SSE."`

4. **SSE аномалия** (`recent_avg_sse` не `None` и `sse_connections > recent_avg_sse * 2`
   и `sse_connections > 20` — двойной порог, чтобы не шуметь на переходе с 2 до 5
   соединений при почти нулевом трафике):
   `"Открыто {sse_connections} SSE-подключений (обычно ~{recent_avg_sse:.0f}). Проверьте, не держит ли один IP непропорционально много соединений (бот/зависший клиент в цикле переподключения) — nginx уже режет по 50 на IP. Проверьте также, не лёг ли Redis (без него SSE не рассылает уведомления, но клиенты всё равно держат соединение)."`

Если ни одно условие не сработало (алерт вызван комбинацией факторов, каждый из
которых по отдельности ниже порога, но вместе дали высокий `load_score`) — список
пуст, к уведомлению/строке таблицы советы просто не добавляются (не выдумываем совет
на пустом месте).

`recent_avg_sse` вычисляется вызывающей стороной (не самой функцией — это её единственная
внешняя зависимость, оставляем снаружи ради тестируемости): среднее `sse_connections`
за последний час через уже существующий `collector.query()`.

### Изменения существующего кода

- `_send_ntfy_alert()` — перед сборкой `body` вызывает `generate_suggestions(point,
  recent_avg_sse)`, при непустом списке добавляет в текст блок:
  ```
  Рекомендации:
  • {совет 1}
  • {совет 2}
  ```
- `_write_alert()` (запись в CSV) — **не меняется**. Советы не хранятся в CSV
  (сырые числа остаются единственным источником истины), пересчитываются на лету при
  каждом чтении — так улучшения логики `generate_suggestions()` в будущем сразу
  применяются и к старым алертам, без миграции CSV.

### Новый эндпоинт

`GET /api/admin/metrics/alerts?limit=50` (`api_require_auth`, тот же паттерн, что
`/api/admin/metrics`) — читает `high_load_alerts.csv` (тот же путь, что уже использует
`MetricsCollector._alerts_path`, нужен геттер или проброс пути), отдаёт последние
`limit` строк (по умолчанию 50, максимум 200) в обратном хронологическом порядке, каждая
строка — dict с исходными колонками CSV плюс поле `suggestions: list[str]` (через
`generate_suggestions()` с тем же способом получения `recent_avg_sse`, что и у
`_send_ntfy_alert()`). Файла нет или пуст — `{"alerts": []}`, не ошибка.

## Frontend

### Новая вкладка «Мониторинг»

По образцу существующих вкладок `/admin` (`ADMIN_TAB_STORAGE_KEY`/`switchTab()` —
общий уже существующий механизм, ничего нового не изобретаем):

```html
<button class="admin-tab" onclick="switchTab('monitoring', this)">Мониторинг</button>
...
<div id="tab-monitoring" class="admin-tab-content" style="display:none">...</div>
```

Логика — новый файл `static/js/admin-monitoring.js` (по прецеденту вкладки
«Трансляция» → `krasmarafon-broadcast-posts.js`, не раздувает и без того большой
инлайн-скрипт `admin.html`).

### 1. Живой блок (сверху)

Плитки текущего снимка: CPU%, RAM (used/total MB + %), среднее время ответа,
запросы/ошибки, SSE-соединения, уникальные IP, аптайм — и отдельно крупная плитка
индекса нагрузки с цветом по русской метке (Низкая=зелёный, Умеренная=жёлтый,
Высокая=оранжевый, Критическая=красный — тот же принцип, что уже используют
`age-group-tag--error` и подобные цветовые маркеры в проекте).

Обновление — подписка на уже существующий `/api/admin/metrics/live` через `SSEClient`
(`static/js/realtime.js`, тот же класс, что и везде в проекте). Одно сообщение — одна
точка метрик, просто перерисовывает плитки.

### 2. Графики истории

Line-чарты (Chart.js, `static/lib/chart4/chart.umd.min.js`) — CPU%, RAM%, среднее время
ответа, ошибки — над одной осью времени. Переключатель диапазона: пилюли/селект
1ч/6ч/24ч/7д/30д/90д/полгода/год → `hours` в `/api/admin/metrics?hours=`, дефолт 24ч.
Смена диапазона перезапрашивает и перерисовывает.

### 3. Таблица последних алертов

Дата/время, цветной бейдж метки нагрузки, ключевые цифры (CPU/RAM/среднее время),
советы (список `•`-строк) — из `/api/admin/metrics/alerts?limit=50`. Обновляется при
открытии вкладки и после каждого нового алерта, полученного через живой SSE-поток (не
отдельным поллингом — просто перезапрашиваем таблицу, когда `load_score` из живой
точки пересекает порог «Высокая»/«Критическая»).

## Обработка ошибок

- SSE-переподключение при разрыве — штатное поведение браузера (`EventSource`
  автопереподключается, свой ретрай, как и везде в проекте, не пишем).
- Нет данных вообще (только что перезапущен сервис, БД метрик пустая) — графики и
  таблица показывают пустое состояние («Нет данных за выбранный период»), не JS-ошибку.
- `generate_suggestions()` — чистая функция без внешних вызовов, упасть не может;
  неожиданный/неполный `point` просто не добавит совет по соответствующему пункту
  (используются `.get()` с дефолтами, не прямой доступ по ключу).
- `/api/admin/metrics/alerts` — файла нет/пуст/битый CSV → `{"alerts": []}`, не 500.

## Тестирование

- Python unit-тесты на `generate_suggestions()` (`tests/unit/test_monitoring_collector.py`
  или новый файл) — по одному кейсу на каждый из 4 факторов отдельно, комбинация
  нескольких факторов сразу, отсутствие всех факторов (пустой список), граничные
  значения порогов.
- Python unit/integration-тест на `/api/admin/metrics/alerts` — пустой CSV, реальные
  строки, `limit`, авторизация (401 без токена — тот же паттерн, что у остальных
  `/api/admin/*`).
- JS-тесты (`node:vm`, тот же приём, что и у остальных JS-тестов проекта без выделенного
  фреймворка) — рендер плиток по фикстурной точке метрик, рендер таблицы алертов по
  фикстурному списку, переключение диапазона дёргает `/api/admin/metrics` с правильным
  `hours`.
- Живая проверка в браузере (agent-browser) на реальных/синтетических данных с прод-БД
  метрик (она уже наполняется) — открыть `/admin` → «Мониторинг», убедиться, что живой
  блок обновляется, графики рисуются, таблица алертов показывает реальные алерты
  18-19.08 с осмысленными советами.

## Явно вне объёма

- Netdata — отдельный инструмент, не трогаем, не встраиваем в `/admin`.
- Изменение порогов/весов `_load_score()` — используем как есть, не пересматриваем
  формулу индекса нагрузки в рамках этой задачи.
- Хранение вычисленных советов в CSV/SQLite — считаются на лету при каждом запросе.
- Собственный ретрай/backoff для SSE на дашборде — полагаемся на нативный `EventSource`.
- Email-уведомления, второй канал уведомлений кроме ntfy — не запрошено.
