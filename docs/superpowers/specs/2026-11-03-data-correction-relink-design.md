# Исправление данных участника: перепривязка заявки/результата к верной карточке — дизайн

Дата: 2026-11-03. Статус: согласован с пользователем (brainstorming), ждёт ревью спецификации.
Связано: личный кабинет Б1 (`2026-11-03-athlete-cards-history-design.md`, раздел «Доработки после локальной
проверки»), Obsidian «текущие приоритеты».

## Проблема

Карточка (`clients.id`) назначается заявке/результату **один раз — триггером при вставке** (`trg_leads_before_insert`:
по точным ФИ+ДР или новая карточка; `trg_results_before_insert`: заявка того же номера с теми же ФИ, иначе ФИ+ДР,
иначе новая). Дальше `client_id` никто не пересчитывает.

Слоты между людьми **не передаются** (ответ пользователя). Правят **ошибочные данные**: человек регистрировал себя,
а автозаполнение подставило чужую ДР/фамилию и т.п. При вставке такая заявка ушла на карточку другого человека
(например, мамы — с такими ФИ+ДР) или создала «фантомную» карточку. Исправляют:
- в стартовом списке (`/admin` → «Изменить»; позже станет основным способом),
- в CRM Tilda → к нам приходит через импорт Excel (совпадение по `order_id`),
- в Excel перед выгрузкой в Copernico / в самом Copernico → к нам приходит в **результатах** (загрузчик по номеру).

После исправления строка остаётся на неверной карточке: в истории кабинета — чужие строки (кабинет их сейчас
отфильтровывает, но свою заявку человек не видит), контакты чужой карточки перезаписываются (`trg_leads_after_update`).

## Правило перепривязки (решение пользователя)

После правки **ФИ или ДР** заявки или результата карточка выбирается заново — как при создании, но по исправленным
данным (точное совпадение нормализованных ФИ+ДР, как в `uk_client(surname, name, birthday)`):

| Ситуация после правки | Действие |
|---|---|
| ФИ+ДР совпадают с текущей карточкой | ничего |
| Есть **другая** карточка с такими ФИ+ДР | строка переезжает на неё (`dq_actions.move_row`, существующая операция «Перенести», отменяемая); опустевшая прежняя карточка удаляется (так уже делает `move_row`) |
| Такой карточки нет, у текущей карточки **других строк нет** (создана по ошибочным данным) | карточка переименовывается: ФИ+ДР по исправленной строке (`dq_actions.edit_record('clients', …)`, отменяемая) |
| Такой карточки нет, у текущей **есть другие строки** (чужая карточка) | новая карточка по исправленным данным и перенос строки туда (`move_row(..., new_card=…)`, отменяемая) |

ДР-заглушка (`1900-01-01`/пусто) — как у триггера: совпадение по ФИ+ДР-заглушке не ищется; если у строки ДР-заглушка,
перепривязка не выполняется (нечего надёжно сопоставлять) — остаётся «Качеству данных».

Каждое действие — запись в журнал «Качества данных» (`dq_actions`) с `done_by` и пометкой источника (`relink`:
`admin` / `import` / `loader`) и **отменяется** штатной отменой. Привязки личного кабинета обрабатываются общим
правилом (карточка существует и ДР совпадает) и склейкой — отдельно ничего не нужно.

Реализация — одна функция (например `dq_actions.relink_row(conn, table, row_id, user, source)`), её вызывают все пути.

## Где срабатывает

1. **«Изменить» в стартовом списке** (`PATCH` заявки → `db_results.update_lead`). Перед сохранением, если правка
   ФИ/ДР приведёт к переезду, — **предупреждение** (решение пользователя): «Заявка переедет на карточку №1234 —
   Иванов Иван, 12.03.1990, 5 заявок, 3 результата. Сохранить?» (для новой карточки — «Будет создана новая
   карточка»; для переименования — «Карточка №… будет переименована»). Нужен эндпоинт предпросмотра
   (что произойдёт) — без изменения БД; сохранение — как сейчас + `relink_row`.
2. **Импорт Excel Tilda** (`bulk_import_leads`, обновление существующих строк по `order_id`): после обновления ФИ/ДР —
   `relink_row` автоматически; в отчёте импорта — «перенесено на другую карточку: N» (и список номеров заказов).
3. **Загрузчик результатов** (`load_race_results.py`, непрерывный режим `_update_existing`, обновление по номеру):
   если пришли другие ФИ/ДР — `relink_row` для результата; в лог загрузчика — строка о переезде.

## Заявка, расходящаяся с исправленным протоколом (решение пользователя: вариант B)

Если исправление пришло только в результат (правили Excel/Copernico, а не Tilda), заявка с тем же номером в том же
забеге остаётся со старыми данными на старой карточке. Автоматически её **не трогаем**. В «Качестве данных» —
находка «Заявка и результат №N расходятся» (если такой проверки ещё нет — добавить; сверить с существующими
`check_lead_on_other_card`/R-LEAD, чтобы не дублировать и чтобы они не предлагали **склейку** карточек в этом случае)
с кнопкой **«Исправить заявку по протоколу»**: ФИ+ДР заявки := из результата, затем `relink_row` (заявка уедет
за результатом). Отменяется штатно.

## Попутные исправления (из разбора)

- **Смена дистанции в «Изменить»** (`update_lead`): `event_id` не пересчитывается → заявка остаётся на старом событии,
  результат к ней не находится. Пересчитывать `event_id` и дубли как `dq_actions.edit_record` (`_lead_event_id`,
  `recompute_duplicates`).
- **Удаления при импорте «файл — источник истины»** — без журнала. Писать удалённые строки в `dq_actions` (как
  `delete_lead()`), чтобы было видно, что и когда удалено.

## Вне рамок

Передача слота между людьми (не практикуется); правка почты/телефона; ДР-заглушки (остаются «Качеству данных»);
пересчёт исторических неверных привязок (их ловят существующие проверки «Качества данных»).

## Тесты

- Unit: выбор действия по 4 случаям правила, ДР-заглушка.
- Интеграция (локальная БД, только тестовые данные): каждый случай через `relink_row`; отмена каждого;
  «Изменить» с предпросмотром и сохранением; импорт Tilda с исправленной ДР → переезд + отчёт; загрузчик
  `_update_existing` с новыми ФИ → переезд результата; находка расхождения и кнопка «Исправить заявку по
  протоколу»; смена дистанции пересчитывает `event_id`; удаление при импорте пишется в журнал.
- Ручная проверка пользователем локально (стартовый список: правка ФИ/ДР с предупреждением); выкладка — после его «да».

## Правка почты заявки в «Изменить» (решение пользователя 2026-11-04)

- В форме «Изменить» стартового списка — поле **почта формы** (`leads.email`). Почта кабинета Tilda (`ma_email`)
  не редактируется (подтверждена Tilda кодом).
- Проверка формата — то же правило, что у входа в кабинет (одна почта, без пробелов/запятых/`;<>()"'`, точка в
  домене, ≤ 255); пусто — нельзя. Нормализация `strip().lower()`.
- Правка — запись в журнал `dq_actions` («было → стало», `lead:{id}`), отменяемая (как `edit`).
- Последствия: заказ уходит из `/me` старой почты и появляется на `/me` новой; привязки кабинета (карточка + ДР)
  не меняются; контакты карточки обновляет триггер `trg_leads_after_update` (как и сейчас при смене телефона/города).
- Подсказка под полем: «Исправьте почту и в CRM Tilda, иначе повторный импорт вернёт старую» (импорт обновляет
  заявку по `order_id`).
- Перепривязку карточки смена почты не вызывает (карточка — по ФИ+ДР).
