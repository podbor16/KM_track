# «Качество данных» → дела о людях с вопросами — дизайн

Дата: 2026-10-28. Статус: согласован с пользователем (brainstorming), ждёт ревью спецификации.

## Проблема

Вкладка /admin → «Качество данных» — плоский список находок с набором кнопок. Пользователь (и будущие
операторы без знания внутренней кухни) не понимает:

1. какую кнопку нажать («Склеить», «Исправить…», «Перенести…», «В результат — как в карточке», «Оставить»);
2. в каком порядке — одно исправление порождает новые находки (перенёс → «расходится с карточкой»);
3. что вообще не так — тексты технические («R-CARD … ≠ #53786 … (ДР)»);
4. «зависшие» находки (неизвестна ДР для новой карточки) висят вперемешку с остальными.

Сценарии — все три: разбор после импорта (5–20 находок), генеральная уборка, точечный запрос участника.

Кроме того, публичный профиль участника («История участия») собирается **по совпадению ФИО в строках
результатов** (`src/analytics/db_athletes.py:get_athlete_results_optimized`), а не по карточке: тёзки
(Пцарев-отец и Пцарев-сын) — один профиль, переносы строк между карточками на сайте не видны.

## Решение (обзор)

Три этапа, каждый выкатывается отдельно:

1. **Профиль по карточке** — `/athlete-profile` и поиск работают по `clients.id`.
2. **Дела и вопросы (сервер)** — находки группируются в дела о людях; каждая находка — вопрос
   человеческим языком с готовыми ответами; ответ выполняет цепочку действий целиком.
3. **Новый экран** — очередь дел + дело с вопросами (две панели на компьютере, два экрана на телефоне).

Технические коды (R-CARD и т.п.) в интерфейсе не показываются.

## Этап 1. Профиль участника по карточке

- `GET /api/search-athletes?q=` (есть) → добавить в ответ `client_id` и `events_count`: тёзки — отдельными
  строками с годом рождения.
- Новый `GET /api/athlete/{client_id}` (число) → результаты `WHERE r.client_id = %s` вместо
  `GET /api/athlete/{surname}/{name}` (`surname = AND name =`). Старый путь удаляется (страница одна,
  внешних клиентов API нет).
- `templates/krasmarafon/athlete-profile.html`, страница `/history` и ссылка «профиль» из строки результата
  (`/results`) передают `client_id`.
- Переключатель «История участия» не трогаем (выключен; этап 1 — подготовка к включению).

## Этап 2. Дела и вопросы

### Модули (разделение `src/analytics/data_quality.py`, ~1200 строк)

| Модуль | Что | Откуда |
|---|---|---|
| `src/analytics/dq_checks.py` | `Data`, `load`, правила (`cat_rule`, `real_bd`, …), все `check_*`, `Finding`, `run_checks(data, event_ids=None, card_ids=None)` | перенос из `data_quality.py` + параметр `card_ids` |
| `src/analytics/dq_actions.py` | `merge_cards`, `move_row`, `edit_record`, `delete_result`, `dismiss`, журнал `dq_actions`, `undo_action`, `recent_actions`, `search_cards` | перенос + цепочки (ниже) |
| `src/analytics/dq_cases.py` | группировка находок в дела, ступени, построение вопросов, применение ответа | новый |
| `src/analytics/data_quality.py` | реэкспорт для обратной совместимости (импорт в `admin.py` после импорта заявок, тесты) | остаётся тонким |

### Дело

- **Дело** = связная группа карточек: карточки одной находки связаны; плюс карточки-тёзки с находками
  (та же фамилия после `norm`, `names_compatible` имени). Брат с другим именем в дело не входит.
- **Ключ дела** — наименьший `client_id` группы (`"c<id>"`). Находка без карточек (результат без карточки) —
  своё дело `"r<result_id>"`.
- **Заголовок** — ФИО основной карточки (наибольшее число строк).
- **Статус**: «нужно решить» (есть нерешённые неотложенные вопросы), «отложено» (все вопросы дела отложены),
  решённые дела в очередь не попадают.

### Ступени (порядок вопросов внутри дела)

1. **Кто есть кто**: C-TWIN, R-LEAD, R-FOREIGN.
2. **Лишние строки**: R-DUP.
3. **Поля**: R-CARD, R-CAT, HYG, L-KID.

Вопросы ступени N+1 показываются серыми («откроется после …») пока есть вопросы ступеней ≤ N.
Внутри ступени — по году забега.

### Вопросы

Вопрос: `{id: finding.key, stage, text, hint, answers: [{id, label, recommended, inputs: [...]}]}`.

| Находка | Текст (пример) | Ответы (★ рекомендованный) | Цепочка |
|---|---|---|---|
| C-TWIN | «Пцарев Саша 2013-12-20 и Пцарев Александр 2013-01-01 — один человек?» + предохранители простыми словами | ★ Да, одна карточка [Ф, И, ДР — из `propose_final`] · Нет, разные люди · Не знаю | `merge_cards` (строки получают итоговые ФИО/ДР — уже так) · `dismiss different_people` · отложить |
| R-LEAD | «Результат №1012 записан на А, заявка с этим номером — на Б. Это один человек?» | ★ Да, склеить (если тот же номер) · Нет — результат принадлежит Б · Нет, всё верно · Не знаю | склейка · `move_row` + выравнивание строки · `dismiss keep` · отложить |
| R-FOREIGN | «Детский 2016 записан на Пцарева 1980 г.р. (36 лет). Чей результат?» | ★ каждый подходящий тёзка · Другой человек — новая карточка [Ф, И, ДР] · Всё верно · Не знаю | `move_row` + выравнивание строки · `dismiss keep` · отложить |
| R-DUP auto | «У Иванова „Не стартовал“ №5 и финиш №7. Удалить „Не стартовал“?» | ★ Да · Оставить | `delete_result` · `dismiss keep` |
| R-DUP (2 финиша) | «Два финиша в одном забеге — это два разных человека?» | Да — вынести №… на [тёзка / новая карточка] · ★ Нет, оставить | `move_row` + выравнивание · `dismiss keep` |
| R-CARD | «В протоколе ДР 2014-01-01, в карточке 2014-12-12. Какая верная?» (и/или ФИ) | ★ Из карточки (если в строке заглушка или «ГГГГ-01-01») · Из протокола · Другая [ввод] | правка строки · правка карточки · правка обеих |
| R-CAT | «Ева 2004 г.р. в категории „Девочки 2006-2007“. Что неверно?» | ДР [ввод] · Категория [список по полу] · Пол [+категория] · Всё верно | `edit_record` + места (ниже) · `dismiss keep` |
| HYG | «Записать как „Иванов Иван“ (в протоколе „ИВАНОВ иван“)?» | ★ Да · Вписать вручную [Ф, И] · Оставить | `fix_fio` · `dismiss keep` |
| L-KID | «Заявка на детский забег с ДР 1986 — это ДР родителя?» | ДР ребёнка [ввод] · Перенести на карточку ребёнка (если есть тёзка) · Дистанция [список] · Оставить | `edit_record leads` · `move_row leads` · `dismiss keep` |

### Цепочки (новое по сравнению с текущими действиями)

- **Выравнивание строки после переноса**: `move_row(..., align=True)` проставляет строке ФИО и ДР новой
  карточки (то же, что делает склейка). Снимок «до» — в той же записи журнала; отмена возвращает всё.
- **Конфликт при правке карточки** (ФИ+ДР уже у другой карточки) — не ошибка, а новый вопрос C-TWIN в этом
  деле: «склеить с #…?».
- **Места**: смена категории/пола в строке результата сразу ставит место по правилу «как у соседа снизу»
  (`rank_category[_clean]`, при смене пола — `rank_sex[_clean]`); прежние места — в снимке журнала.
- **«Не знаю» / «Отложить дело»** — `dq_decisions` с `decision='postponed'` и причиной (по умолчанию
  «не знаю ДР») для каждого вопроса дела. Новая находка по делу (новый ключ) возвращает дело в очередь.

### «Живой» забег

Забег «живой», если дата события — сегодня или вчера (Asia/Krasnoyarsk). Вопросы по результатам такого
забега не дают править строку результата: вместо ответов — «Исправьте в Copernico: загрузчик перезапишет
ФИО, ДР, пол, категорию и места». Перенос строки между карточками разрешён (загрузчик не трогает `client_id`).

### API (`src/krasmarafon/routers/data_quality.py`)

| Метод | Что |
|---|---|
| `GET /api/admin/data-quality/cases?status=open\|postponed&event_id=` | очередь: `[{key, title, cards, questions_left, events}]` |
| `GET /api/admin/data-quality/cases/{key}` | дело: карточки со строками по годам (подсветка проблемных), вопросы, живой ли забег |
| `POST /api/admin/data-quality/cases/{key}/answer` `{question_id, answer_id, inputs}` | выполнить цепочку → обновлённое дело (проверки только по карточкам дела) |
| `POST /api/admin/data-quality/cases/{key}/postpone` `{reason}` | отложить дело |
| `GET /api/admin/data-quality/person?q=` | дело по ФИО (даже без находок) — для точечного запроса |
| журнал, отмена, `cards`, `move`, `edit` | как сейчас (ручные действия «⋯») |

Старый `GET /api/admin/data-quality` (плоский список) остаётся до конца этапа 3, потом удаляется.

### Ошибки

- Каждая цепочка — одна транзакция; ошибка → откат, текст ошибки в деле.
- Ответ на устаревший вопрос (строка/карточка изменилась в другой вкладке, ключа находки больше нет) —
  409 «Дело изменилось — обновите».
- Проверки по делу после ответа: `run_checks(load(conn), card_ids=…)`.

## Этап 3. Экран

`static/js/admin-dq-cases.js` (новый) вместо UI в `admin-data-quality.js`; разметка вкладки в
`templates/krasmarafon/admin.html`; стили в `static/css/admin.css`.

- **Сверху**: поиск человека по ФИО (открывает дело) · фильтр «Забег» · вкладки «Нужно решить · N дел» /
  «Отложено · N» / «Журнал».
- **Компьютер (≥ 900 px)**: слева очередь (ФИО, число карточек, «осталось N вопросов»), справа дело.
- **Телефон**: экран очереди → экран дела с «← К списку»; карточки столбиком.
- **Дело**: карточки-тёзки рядом (номер, ФИО, ДР, строки по годам: результаты и заявки; проблемная —
  подсвечена, перенесённая — помечена) · вопросы: решённые — строкой «✓ … · Отменить», текущий раскрыт
  (радиокнопки, ★ выбран по умолчанию, поля ввода, «Применить»), следующие — серые · «Отложить дело»,
  «Следующее дело →».
- **«⋯» у карточки и строки**: перенести строку (поиск карточки по ФИО), склеить с…, исправить поля.
- После действия: «На сайте обновится в течение 5 минут».
- Правка заявки — предупреждение «повторный импорт файла организатора может перезаписать».

## Где отражаются правки (проверяется тестами)

| Где | Источник | Что делаем |
|---|---|---|
| Результаты, трекер, дипломы | строка `results` (кеш ≤ 5 с) | выравнивание строки после переноса; места |
| Стартовые списки, заявки, возвраты, дубли (/admin) | строка `leads`, `refund`, `is_duplicate` (кеш ≤ 5 мин) | `recompute_duplicates` при переносе заявки |
| DataLens | `leads` по `client_id` | — (обновится с датасетом) |
| Карточка (счётчики, первая/последняя заявка) | `clients` | `recompute_aggregates` при каждом действии |
| Профиль участника | после этапа 1 — `results` по `client_id` | этап 1 |

Ограничения (сообщаются в интерфейсе, не чинятся): кеши в памяти каждого из 3 процессов сервера (до 10 мин
для истории прошлого года); повторный импорт заявок из Excel перезаписывает ФИО/ДР заявки; живой загрузчик
перезаписывает поля и места результатов своего забега.

## Тесты

- **unit** (`tests/unit/test_dq_cases.py`): группировка в дела (тёзки по уменьшительному имени, брат — нет),
  ключ дела, ступени и серые вопросы, тексты и рекомендованный ответ для каждого типа, «живой» забег.
- **integration на локальной БД** (`tests/integration/test_dq_cases_db.py`): каждая цепочка ответа + отмена;
  сквозные проверки после ответа через функции страниц — результаты события, стартовый список, список заявок
  с `refund`/`is_duplicate`, профиль по `client_id`, счётчики карточки; отложить/вернуть дело; 409 на
  устаревший вопрос.
- **API** (`tests/integration/test_admin_dq_cases.py`): авторизация, коды ошибок.
- **Браузер**: компьютер и телефон на локальной копии (Пцаревы, Черновы, Ветрова как тестовые случаи).

## Вне рамок

- Защита ручных правок заявок от повторного импорта.
- Сброс кешей в других процессах сервера.
- Включение «Истории участия» (решение пользователя после этапа 1).
- Роли «оператор/администратор» (все действия доступны всем, кто вошёл в /admin; журнал и отмена — защита).
