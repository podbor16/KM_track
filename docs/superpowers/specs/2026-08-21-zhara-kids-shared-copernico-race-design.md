# Жара + Детский забег — общий Copernico race_id, список событий на дистанцию

## Контекст и цель

Организатор передал ID гонки в Copernico: `--2026-6118` — один и тот же race_id обслуживает одновременно Жару (взрослые дистанции) и Детский забег (дети по годам рождения). Внутри одного race_id события различаются полем `event`:

- `5km` — Жара 5 км (21.1 км в Copernico пока не создана)
- `1km-2020`, `1km-2019`, `1km-2018`, `1km-2017`, `1km-2016`, `1km-2015` — Детский забег «1 км», шесть возрастных групп по году рождения, каждая со своей волной старта (шаг 15 мин: 03:30…04:45)

Read-only проверка через реальный Copernico API подтвердила: общий race_id безопасен (каждый запрос фильтруется парой race_id+event, пересечений данных между Жарой и Детьми нет), а номера участников (`dorsal`) не пересекаются между шестью возрастными группами (у каждой свой числовой диапазон). Не проверено (и не может быть проверено заранее) — качество данных по мере того, как организатор довыгружает участников; часть записей уже сейчас приходит плейсхолдером Copernico `"name": "Dorsal sin datos"` — код это уже обрабатывает (пропуск с предупреждением).

Проблема: `RaceLoader` (`load_race_results.py`) устроен как «один процесс = одна дистанция = один Copernico `event`». Детский забег «1 км» — ОДНА наша дистанция (`db_event_id=113`), которой нужны данные из ШЕСТИ разных `event`-значений Copernico. Нужно расширить загрузчик, чтобы одна дистанция могла опрашивать несколько Copernico-событий за один цикл, сохранив полную обратную совместимость с уже настроенными событиями (Весна, Первомайский и т.д.), у которых `event` — всегда одна строка.

## Изменения

### 1. `fetch_from_copernico()` — список событий

`self.copernico_event` может быть строкой (как сейчас) или списком строк. Функция нормализует в список (`[event]` если строка), делает по одному HTTP-запросу на каждый элемент, сливает `runners` всех успешных запросов в один плоский список — код ниже по потоку (`_update_existing()`, `init_mode()`) уже агностичен к тому, из какого под-события пришла строка, менять их не нужно.

`gun_time_utc` обновляется **только когда `copernico_event` — одна строка**. При списке событий (детский забег) у каждой возрастной группы своё время старта — нет одного корректного значения для записи в общее поле `events.gun_time_utc` (одна колонка на весь `db_event_id`), значение остаётся `NULL`. Проверено: `gun_time_utc` не участвует в расчёте мест/времени участников (те считаются из per-runner полей `times.official_:::start:::`/`times.official_:::finish:::`), используется только трекером (у детского забега `tracked: false`) и, возможно, информационным баннером — `NULL` там уже штатно обрабатывается как «не задано».

Ошибка на одном под-событии (таймаут, 5xx и т.п.) логируется и пропускается — не обрывает остальные под-события того же цикла. Cycle завершается с тем, что успело получиться (частичные данные лучше отсутствия любых, дальнейшие циклы догонят пропущенное).

### 2. `zhara.yaml` — дистанция «5 км»

```yaml
copernico:
  race_id: "--2026-6118"
  login: "podbor250718@gmail.com"
  preset: "km_analytics"
  event: "5km"
```

Дистанция «21.1 км» не трогается — `race_id`/`event` там остаются `null`/плейсхолдером, т.к. в Copernico это событие ещё не создано.

### 3. `kids.yaml` — дистанция «1 км»

```yaml
copernico:
  race_id: "--2026-6118"
  login: "podbor250718@gmail.com"
  preset: "km_analytics"
  event:
    - "1km-2020"
    - "1km-2019"
    - "1km-2018"
    - "1km-2017"
    - "1km-2016"
    - "1km-2015"
```

Дистанция «500 м» не трогается (нет блока `copernico` вообще — для неё Copernico не используется).

### 4. `config/copernico/km_analytics.yaml` — новый preset-файл

Файла ещё нет в репозитории — без него загрузчик не запускается (`parser.error` при старте). По образцу уже существующих presets (`km_vesna_5km_2026.yaml` и т.п.):

```yaml
description: "Жара 5км + Детский забег 1км (6 возрастных групп), race_id --2026-6118. Chip-времена не включены в пресет (нет times.real_*). Контрольные точки трассы отсутствуют — единственные КТ-поля, которые сейчас отдаёт Copernico по этому race_id, физически принадлежат дистанции 21.1 км, которой ещё нет в Copernico."

fields:
  bib: dorsal
  surname: surname
  name: name
  birthdate: birthdate
  gender: gender
  status: status
  category: category

time_fields:
  gun_start:   "times.official_:::start:::"
  gun_finish:  "times.official_:::finish:::"
  chip_start:  null
  chip_finish: null

checkpoint_fields: {}
```

`checkpoint_fields: {}` — уже поддерживаемое штатное состояние (`cp_fields = self._preset_cfg.get("checkpoint_fields") or {}`, пустой словарь даёт 0 КТ-колонок без ошибок). Когда 21.1 км появится в Copernico — этот же preset-файл дополнится нужными полями (или для 21.1 км будет создан отдельный preset), не в рамках этой задачи.

## Тестирование

- `fetch_from_copernico()` со списком из 2-3 event-строк — участники всех под-событий попадают в один результирующий список, `gun_time_utc` НЕ обновляется
- `fetch_from_copernico()` с одной строкой (регрессия) — поведение идентично текущему, `gun_time_utc` обновляется как раньше
- Одно под-событие из списка возвращает ошибку (таймаут/5xx) — остальные под-события всё равно попадают в результат, ошибка только логируется
- Пустой список/все под-события упали — возвращается `[]` (текущее поведение `continuous_mode()` на пустой список уже корректно даёт backoff)

## Явно вне объёма

- Дистанция 21.1 км Жары — race_id/event/checkpoint_fields не трогаются, Copernico-событие там ещё не создано организатором
- Сверка реальных КТ-координат/дистанций трассы 5 км и 1 км — не требуется прямо сейчас (Copernico не отдаёт для них релевантных чекпоинт-полей)
- Реальный запуск загрузчика на боевых данных (`--init`/`--continuous`) — по решению пользователя, не в рамках этой задачи (участники ещё не полностью выгружены организатором)
- CLI-флаг для override `copernico.event` на лету — не нужен при выбранном подходе (список задаётся в самом YAML-конфиге)
