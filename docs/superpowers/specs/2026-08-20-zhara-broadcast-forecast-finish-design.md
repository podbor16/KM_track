# Прогноз финиша в live-JSON топ-10 для трансляции — дизайн

## Контекст и цель

Live-JSON топ-10 для режиссёра трансляции Жары (`src/krasmarafon/services/live_top10_export.py::generate_top10_json()`, вызывается из `RaceLoader._maybe_write_broadcast_json()` в `load_race_results.py --continuous --broadcast-json`) уже отдаёт по каждой контрольной точке топ-10 абсолют/муж/жен с текущим временем и темпом участника на этой КТ. Не хватает прогноза, когда участник, ещё бегущий дистанцию, ожидаемо финиширует — режиссёру нужно заранее знать, кого готовить в кадр.

Нужен только прогноз **финишного времени** (elapsed/чистое), без астрономического (wall-clock) времени.

## Алгоритм

Средний темп с начала гонки — то же, что даёт уже существующее и вычисляемое поле `pace_avg_kt{i}` (elapsed/distance до этой КТ). Более точный вариант («темп последнего отрезка между двумя соседними КТ») сознательно НЕ выбран в этот раз — он использовался на похожей фиче Siberman, но требует доп. данных (соседняя КТ) и решено не усложнять первую версию.

```
remaining_km = event_distance - checkpoint_distances[i]
forecast_seconds = time_clear_seconds + remaining_km × pace_avg_seconds_per_km
```

`time_clear_seconds` и `pace_avg_seconds_per_km` — уже читаемые из БД и конвертируемые в `_build_checkpoint()`/`build_list()` значения (`_td_to_seconds()` от `time_clear`/`pace_avg`), новых запросов к БД не требуется. `event_distance` и `checkpoint_distances[i]` — уже доступны в `generate_top10_json()` (используются для `label`/`distance`).

## Формат и место в JSON

Новое поле `forecast_finish_time` (строка `чч:мм:сс`, тот же формат, что уже даёт `_seconds_to_hms()`) — в каждой записи top10-списков (`top10_absolute`/`top10_male`/`top10_female`) **только у промежуточных КТ** (`kt1`...`ktN`).

В блоке `finish` (участник уже финишировал, есть реальное время) поле `forecast_finish_time` **отсутствует в записи** (не добавляется вовсе, не `null`) — структура записи в `finish` остаётся такой же, как сейчас.

Пример записи на промежуточной КТ:

```json
{
    "start_number": 142,
    "surname": "Иванов",
    "name": "Пётр",
    "sex": "M",
    "city": "Красноярск",
    "rank_absolute": 1,
    "rank_sex": 1,
    "time": "01:10:00",
    "pace": "4:40",
    "gap_absolute": "Лидер",
    "gap_sex": "Лидер",
    "photo_url": "...",
    "forecast_finish_time": "01:40:30"
}
```

## Граничные случаи

- `pace_avg` отсутствует (`None`) в исходных данных — поле `forecast_finish_time` для ЭТОЙ записи тоже не добавляется (не падает, просто нет прогноза для конкретного участника — тот же принцип, что уже применяется к `pace` в текущем коде).
- `remaining_km` близко к нулю или отрицательно (последняя КТ почти совпадает с финишем, либо `checkpoint_distances` содержит неточность) — формула не требует спецобработки, даёт прогноз ≈ текущему времени; отрицательный `remaining_km` даёт прогноз чуть МЕНЬШЕ текущего времени на КТ, что при таких небольших расстояниях не вводит в заблуждение на практике.

## Явно вне объёма

- Астрономическое (wall-clock) время прогноза — не нужно.
- Прогноз времени НА промежуточных КТ (не финиша) — не запрошено.
- Изменение блока `finish`.
- Алгоритм «темп последнего сегмента» — рассмотрен, отклонён в пользу простоты для первой версии.

## Тестирование

- Unit-тест на саму формулу прогноза (изолированная функция, без БД) — типовой случай, случай с `pace_avg=None` (поле отсутствует в результате), случай `remaining_km<=0`.
- Тест на `generate_top10_json()`/`_build_checkpoint()` — поле `forecast_finish_time` присутствует у промежуточных КТ и отсутствует в блоке `finish` (round-trip на фикстурных данных, без реального MySQL — по образцу существующих тестов этого модуля).
