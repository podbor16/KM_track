# Личный кабинет, этап Б2: представители — дизайн

Дата: 2026-11-04. Статус: согласован с пользователем (brainstorming), ждёт ревью спецификации.
Продолжение Б1 (`2026-11-03-athlete-cards-history-design.md`). Схема «аккаунт ≠ спортсмен», п.2 — Obsidian
`inbox/2026-11-03-krasmarafon-athlete-auth`.

## Цель

Аккаунт (почта) получает доступ к истории другого человека — ребёнка, пожилого родителя, подопечного, — которого
он записывал на забеги, подтвердив его дату рождения. Владелец карточки (заявивший её «Это я») видит своих
представителей и может убрать любого.

## Правила (решения пользователя)

- **Стать представителем** карточки можно, если (1) на почте аккаунта есть заявка **этого человека** — то же
  правило, что у права заявить «Это я» (`athlete_claims.same_person`: заявка карточки с близкими ФИ и совместимой
  ДР), и (2) введённая ДР совпадает с ДР карточки (`clients.birthday`, не заглушка). Любой возраст.
- Представителей у карточки может быть **несколько** (оба родителя, тренер). Аккаунт не может быть представителем
  своей же заявленной карточки.
- Лимит — общий с «Это я»: 5 неверных ДР на (аккаунт, карточку) за сутки (`athlete_claim_attempts`).
- **18 лет — ничего не меняется** (вариант A): доступ сохраняется; повзрослевший, заявив свою карточку, видит
  представителя в списке и может убрать.
- Тренер формально проходит по правилу — принято (каждый может его убрать).
- **Уведомление** при получении доступа — на почты из заявок карточки (тот же отбор, что `notify_recipients`,
  без почты аккаунта): «Доступ к истории забегов {ФИ} на сайте результатов Красмарафона получил аккаунт {маска}.
  Если вы не знаете этого человека — напишите нам на 1@krasmarafon.ru». В фоне (`BackgroundTasks`).
- **Действительность** — то же общее правило, что у привязки «Это я»: карточка существует и её ДР = ДР,
  подтверждённой представителем; иначе доступ снимается при открытии кабинета (журнал, пояснение на `/me`
  «Данные карточки изменились — подтвердите заново»).
- **Склейки** переносят доступы на итоговую карточку так же, как привязки (`client_merge.apply`); дубль доступа
  (тот же аккаунт уже представитель итоговой) — снимается. Отмена склейки возвращает (как у привязок).

## Интерфейс

**`/me`** — у человека группы (есть `client_id`, `can_claim` — заявка этого человека с почты аккаунта), не
заявленного этим аккаунтом и без действующего доступа, — две кнопки на `<details>`: **«Это я»** (как сейчас) и
**«Я представитель»** (поле «Дата рождения этого человека» + «Подтвердить», `POST /me/rep`). Удача → плашка
**«Вы представитель · История →»** (`/me/athlete/{client_id}`). Ошибки — у формы, тексты как у «Это я»
(`mismatch`, `limit`, `no_birthday`, `not_yours`), плюс `own` «Это ваша карточка — откройте свою историю».
Сообщение `OTHER_PERSON` у «Это я» меняется на: «У вас уже есть своя карточка с другой датой рождения. Если это
ваш ребёнок или близкий — нажмите «Я представитель»».

**`/me/athlete/{client_id}`** — история подопечного: та же страница, что `/me/history` (вкладки «Результаты» /
«Заявки», итоги), для одной карточки. Доступ — только при действующем доступе представителя (иначе 404; своя
заявленная карточка → редирект на `/me/history`). В «Подробнее» — как у своей истории (участник, оформлено,
номер заказа, сумма, промокод, состав, почта оформления — маской, если не почта аккаунта); телефона и почт
человека нет (их и сейчас нет). Внизу: «Сообщить об ошибке» и «Отказаться от доступа» (`POST /me/unrep`,
`confirm()`).

**Блок «Доступ к вашей истории»** — внизу `/me/history` владельца: список действующих представителей его
заявленных карточек (почта маской, дата получения доступа) и у каждого «Убрать» (`POST /me/rep/remove`,
`confirm()`). Нет представителей — блок не показывается.

## Данные

Миграция `migrations/athlete_reps.sql` (идемпотентно, **без «;» в комментариях**):

```sql
CREATE TABLE IF NOT EXISTS athlete_reps (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  email VARCHAR(255) NOT NULL,
  client_id INT NOT NULL,
  birthday DATE NOT NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uq_ar (email, client_id),
  KEY idx_ar_client (client_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

Журнал `dq_actions`: `athlete_rep` / `athlete_unrep` (`finding_key` = `client:{id}`, `details` = почта,
причина: `user` / `owner_removed` / `card_deleted` / `birthday_changed` / `merged`).

## Код

- `src/krasmarafon/services/athlete_reps.py` — `become_rep(email, client_id, birthday) -> RepResult`,
  `rep_cards(email) -> (действующие, снятые)` (общее правило), `remove_rep(email, client_id)`,
  `remove_rep_by_owner(owner_email, rep_id)`, `reps_of(owner_email) -> list`, `notify_rep(client_id, email)`.
  Переиспользовать из `athlete_claims`: `same_person`, проверку «заявка этого человека на почте», лимит попыток,
  журнал, `history_rows`, `notify_recipients`, `mask_email`.
- `client_merge.apply` / `dq_actions._restore_claims` — доступы представителей вместе с привязками.
- Роутер `athlete.py`: `POST /me/rep`, `POST /me/unrep`, `POST /me/rep/remove`, `GET /me/athlete/{client_id}`;
  `/me` — плашки и формы; под переключателем «Личный кабинет».
- Шаблоны: `me.html` (кнопка/плашка), `me-history.html` переиспользуется для подопечного (флаг «чужая история»),
  блок представителей.

## Тесты

- Интеграция (только тестовые данные): стать представителем (верная/неверная ДР, лимит, без ДР, не из заявок
  почты → not_yours, своя карточка → own); несколько представителей; доступ к `/me/athlete/{id}` (есть/нет
  доступа, своя → редирект, кабинет выключен → 404); владелец видит и убирает; отказ от доступа; уведомление
  (адресаты без почты аккаунта); общее правило (правка ДР карточки → доступ снят + пояснение); склейка переносит,
  отмена возвращает; Origin на POST.
- Скриншоты `/me` и `/me/athlete/{id}` (1280, 390) перед передачей; ручная проверка пользователем; выкладка —
  после «да» (миграция + push).
