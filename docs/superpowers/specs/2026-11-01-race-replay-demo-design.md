# Демо «Повтор гонки» на GitHub Pages — часть 1: ядро + Красмарафон

**Дата:** 01.11.2026
**Основание:** ТЗ «Демо-стенд „Повтор гонки“» v1.0 (заказчик — Матвей Подборский), пересмотрено в обсуждении 01.11.2026.
**Цель:** публичная ссылка, по которой потенциальный клиент (организатор, хронометражист) в любой момент видит прошедшую гонку «вживую»: маркеры движутся по карте, участники проходят КТ и финишируют, работают поиск и карточка участника.

## 1. Отличия от исходного ТЗ (согласованы)

| ТЗ | Решение | Почему |
|---|---|---|
| Отдельный сервер, демо-БД, replay-сервер под Copernico, systemd, поддомен | Статический сайт на GitHub Pages, повтор целиком в браузере | Бесплатно, не может повлиять на прод, всегда доступно |
| Повтор через настоящий конвейер загрузчик → БД → API/SSE | Запись собирается заранее **тем же серверным кодом**, браузер её проигрывает | Без сервера конвейер не запустить; логика прода при этом не дублируется |
| Ускорение — отдельный этап 3 | Сразу: 1×/2×/5×/10× и перемотка | В схеме с виртуальными часами почти бесплатно |
| Стартовые номера сохраняются | Номера перемешиваются | Протокол Жары публичный: по реальному номеру находится реальный человек рядом с выдуманным именем |
| `/admin/demo`, `ctl.py`, режим `loop` на сервере | Панель управления в самой странице, круг повтора в браузере | Сервера нет |
| Нагрузочное тестирование (второе ТЗ) | Не делается | Решение заказчика |

## 2. Состав работ и разбиение

Работа разбита на части, у каждой своя спецификация и план:

1. **Ядро + Красмарафон (этот документ):** виртуальные часы, подмена источников данных, панель управления, витрина, сборка и публикация; гонки **Жара 21,1 км** (event 116) и **Жара 5 км** (event 115).
2. Siberman — live-результаты (`/api/siberman/results`, опрос 20 с).
3. Триатлет 24 ч (`/api/tri/standings`, `/api/tri/laps`, опрос 30 с).
4. Дуатлон 222 (`/api/duathlon222_{год}/standings`, опрос 30 с).

Формат записи и подмена `fetch` в части 1 делаются общими, чтобы части 2–4 добавлялись без переделки ядра.

## 3. Архитектура

```
локальная БД (MySQL :3308, снимок прода) + config/events/zhara.yaml + GPX
   │
   ▼  tools/demo/build.py zhara_21 zhara_5
   ├─ record.py      обезличивание + проигрывание гонки шагом 5 с серверным кодом
   │                 → dist/data/<race>.json.gz
   ├─ site.py        рендер витрины и tracker.html (Jinja), копирование статики,
   │                 переписывание путей /static/… → относительные
   └─ checks.py      ПДн, битые ссылки, неперехваченные /api/
   │
   ▼  tools/demo/publish.py → репозиторий podbor16/race-tracker-demo (Pages, ветка main)

Браузер: demo-replay.js (подключается ДО utils.js/tracker-*.js)
   ├─ виртуальные часы (Date.now / new Date())
   ├─ подмена fetch: /api/current-event, /api/event-results
   ├─ поддельный EventSource: /api/sse/tracker
   └─ панель управления + круг повтора
```

Код живёт в `tools/demo/` основного репозитория (скрипты, шаблоны шапки и витрины, `demo-replay.js`). `dist/` в основной репозиторий не коммитится (`.gitignore`). Прод-статика и прод-шаблоны не меняются; прод-Python — только п. 3.1.

### 3.1. Правки прод-кода (только эти)

Из `_do_build()` в `src/krasmarafon/services/results_service.py` выносится чистая функция «строки результатов + данные события + исторические скорости + момент времени → ответ трекера», без обращений к БД. `_do_build()` вызывает её после загрузки данных; поведение прода не меняется. `calculate_live_position()` получает необязательный параметр `now` (по умолчанию `datetime.now()`), чтобы сборка могла считать положение на момент T. Тело эндпоинта `/api/current-event` выносится в `build_current_event_response(event)` — сборка берёт из неё конфиг гонки для демо.

## 4. Данные и обезличивание

**Источник:** локальная БД (`.env.local`, MySQL80 :3308, база `krasmarafon`), таблица `results` по `event_id`; `events` — время выстрела и КТ; конфиг гонки и GPX — из `config/events/zhara.yaml`. К продовой БД сборка не обращается.

**Обезличивание (до записи файла):**
- ФИО → сгенерированные русские фамилия и имя; пол сохраняется; генерация детерминирована по исходному `id` (одно имя на участника при пересборке).
- `birthday`, `client_id` → удаляются (`null`). Пол (`sex`) и `category` сохраняются.
- `start_number` → перемешивается внутри гонки без повторов (детерминированно, с фиксированным seed). Признаки `is_elite`, `is_pacer` сохраняются.
- `id` → перенумеровывается 1..N.
- Личные скорости прошлого года (`hist_data.personal`, ключ — реальные ФИО+ДР) считаются на реальных данных при сборке; в запись попадает только итоговое число `speed`.

**Проверка:** `checks.py` ищет в `dist/` все фамилии, имена, телефоны и email участников этой гонки из БД (в т.ч. в сжатых данных). Любое совпадение — сборка падает.

## 5. Запись гонки

**Проигрывание.** Виртуальный момент T идёт от `gun − 5 мин` до `последний финиш + 5 мин` шагом 5 с (темп прод-загрузчика). На каждом шаге:
1. у каждого участника обнуляются времена, которые наступают позже T (момент от выстрела: старт — `time_gun_start`, КТ — `time_clear_ktN`, который несмотря на имя хранит official-время от выстрела, финиш — `time_gun_finish`);
2. статус: нет старта к T → не стартовал; старт есть, финиша нет → на дистанции; финиш ≤ T → финишировал; DNF/DSQ — только после последнего финиша;
3. места пересчитываются среди финишировавших к T функцией ранжирования загрузчика (`_assign_ranks` из `load_race_results.py`);
4. ответ трекера строится вынесенной функцией из п. 3.1 с `now = T`;
5. изменения относительно предыдущего шага определяются той же функцией, что у прод-SSE (`_tracker_runner_changed`).

**Формат** `<race>.json.gz`:
```json
{
  "meta": {
    "race": "zhara_21", "title": "Жара, 21,1 км", "caption": "Жара, Красноярск, 23.08.2026 — запись реальной гонки",
    "current_event": { "...": "ответ /api/current-event" },
    "gun_unix_ms": 0, "step_s": 5,
    "loop_start_s": 1800, "loop_end_s": 0,
    "marks": [{"label": "Старт", "t_s": 0}, {"label": "Первый финиш", "t_s": 0}, {"label": "Массовый финиш", "t_s": 0}],
    "gpx": "static/map/2026/zhara_21.gpx"
  },
  "initial": { "...": "полный ответ трекера на момент начала записи" },
  "changes": [ { "t_s": 5, "results": [ "изменившиеся участники без current_distance" ] } ],
  "distance": { "<id>": [[t_s, km], ...] }
}
```
- `t_s` — секунды от выстрела.
- **`current_distance`** хранится отдельно как ломаная: точки излома, при которых линейная интерполяция отклоняется от реального значения не более чем на 1 м. Браузер достраивает значение между точками.
- `loop_end_s` = момент «массового финиша» (финишировали 95% финишировавших) + 5 мин. «Первый финиш» и «Массовый финиш» вычисляются по данным.
- Ожидаемый размер — 1–2 МБ после сжатия.

## 6. Браузер

**Адреса** (на `podbor16.github.io/race-tracker-demo/`):
- `/` — витрина: карточки гонок (название, дата, дистанция, участники, тип «трекер на карте»), кнопка «Открыть»;
- `/zhara-21/`, `/zhara-5/` — трекер;
- параметры `?t=45m&speed=5` — открыть нужный момент и скорость.

**Виртуальные часы:** `время_гонки = опора + (performance.now() − опора_реал) × скорость`. `Date.now()` и `new Date()` без аргументов возвращают время гонки; `new Date(x)` работает как обычно. Даты в записи настоящие (23.08.2026). Пауза = скорость 0.

**Подмена источников:**
- `fetch('/api/current-event')` → `meta.current_event`;
- `fetch('/api/event-results…')` → состояние на текущее время гонки;
- `new EventSource('/api/sse/tracker…')` → поддельный поток: первым сообщением полный снимок (`initial: true`), далее раз в 5 с времени гонки — изменения (`initial: false`) с `current_distance`, интерполированным на этот момент, для всех бегущих (как у прода);
- прочие запросы `fetch` проходят без изменений (GPX, статика).

**Перемотка:** новый полный снимок в поток (`initial: true`). Если в браузерной проверке анимация маркеров при перемотке назад сбивается — перемотка через перезагрузку страницы с `?t=` (решение фиксируется в плане по итогам проверки).

**Круг повтора:** старт с `loop_start_s` (30-я минута); при достижении `loop_end_s` — перемотка на `loop_start_s`.

**Панель управления** (полоса внизу; на телефоне сворачивается в кнопку): ▶/⏸; скорость 1×·2×·5×·10×; ползунок времени гонки с отметками из `meta.marks` и текущим временем; подпись `meta.caption`.

**Шапка:** нейтральная — «← Все демо» и название гонки; без навигации Красмарафона и без счётчика Метрики. Футер Красмарафона не выводится.

**Ошибки:** запись не загрузилась → сообщение «Не удалось загрузить запись гонки» и кнопка «Повторить»; неизвестная гонка → переход на витрину.

## 7. Сборка и публикация

- `python tools/demo/build.py zhara_21 zhara_5` → `dist/`: запись, страницы, только нужная статика (Leaflet, CSS, JS трекера, GPX, иконки), `.nojekyll`. Пути `/static/…` в HTML/CSS/JS → относительные.
- Проверки (`checks.py`), провал любой → сборка падает: ПДн (п. 4); все локальные ссылки существуют; в коде страниц нет обращений к `/api/`, кроме перехватываемых.
- `python tools/demo/publish.py` → коммит содержимого `dist/` в `podbor16/race-tracker-demo`, ветка `main`. Репозиторий и включение Pages — один раз, с подтверждения заказчика.
- Добавить гонку Красмарафона = запись в списке гонок сборки (код события и `event_id`) + пересборка; кода не менять.

## 8. Проверка

**pytest (`tests/unit/`):**
- обезличивание: детерминированность, пол сохранён, нет реальных ФИО/ДР/`client_id`, номера — перестановка без повторов;
- запись: восстановленное из записи состояние в каждый шаг T совпадает с ответом серверного кода (все поля точно, `current_distance` — до 1 м);
- точность: в конце записи места и времена всех участников совпадают с итоговыми в БД (кроме обезличенных полей);
- вынос чистой функции из `_do_build`: весь существующий набор тестов проходит.

**Браузер** (локальный HTTP-сервер на `dist/` под путём `/race-tracker-demo/`; десктоп и 390 px):
- через 10 с после открытия маркеры движутся;
- ползунок, скорости, пауза, круг повтора;
- поиск участника и карточка;
- в консоли нет ошибок; ни одного сетевого запроса к `/api/`.
