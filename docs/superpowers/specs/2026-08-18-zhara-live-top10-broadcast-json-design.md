# Live-топ-10 по отметкам для трансляции Жары — дизайн

## Контекст и цель

Режиссёру трансляции Жары 2026 нужны данные топ-10 участников на каждой контрольной
точке — для вывода в прямой эфир. Данные должны обновляться в реальном времени по ходу
гонки. Формат — статичный, периодически перезаписываемый JSON-файл (не API-эндпоинт,
не Google Таблица — решено в ходе брейншторминга).

## Объём

- **Дистанции**: только «5 км» и «21.1 км» — у «2 км» нет промежуточных контрольных
  точек вообще (`events.checkpoint_distances IS NULL`), топ-10 по отметкам для неё не
  имеет смысла.
- **Отметки**: все промежуточные КТ + финиш каждой дистанции. По актуальному конфигу
  событий (`events.checkpoint_distances`):
  - «5 км» — `[0, 2.5, 5.0]` → 1 промежуточная точка (kt1) + финиш
  - «21.1 км» — `[0, 6.0, 6.5, 10.5, 15.5, 16.0, 20.0, 21.1]` → 6 промежуточных точек
    (kt1…kt6) + финиш
- **На каждой отметке — 3 списка**: топ-10 абсолют, топ-10 мужчины, топ-10 женщины
  (раздельно, не единый список с пометкой пола).
- **«Официальное» время/место на отметке** = чистое время (`time_clear_kt*`,
  `rank_absolute_kt*`, `rank_sex_kt*`, `pace_avg_kt*` в таблице `results`). Отдельного
  gun-time на уровне промежуточных отметок в БД не существует (gun есть только на
  старте/финише) — и это совпадает с уже принятым в этом же сезоне решением, что для
  Жары официальным считается именно чистое время (см. коммит `9b1d549`,
  «Жара — награждение по чистому времени вместо официального»).

## Источник данных

Все нужные поля на уровне отметки уже вычисляются и хранятся `load_race_results.py`
в live-режиме (`--continuous`, тот же процесс, что уже используется во время гонки для
women7/«Достигая цели»):
- `results.time_clear_kt1..kt7`, `pace_avg_kt1..kt7`
- `results.rank_absolute_kt1..kt7`, `results.rank_sex_kt1..kt7`
- `results.surname`, `.name`, `.sex`, `.start_number`
- `clients.city` — джойн по `results.client_id = clients.id`

Дополнительно вычисляется на лету при сборке JSON:
- **Отставание от лидера** (`gap_absolute`/`gap_sex`) — разница чистого времени на
  данной отметке относительно первого места в СВОЁМ списке (лидер абсолюта — для
  `gap_absolute`, лидер своего пола — для `gap_sex`), формат `+ММ:СС` (`ЧЧ:ММ:СС`, если
  отставание ≥ часа); у самого лидера — строка `"Лидер"`.

Фото — из новой таблицы `participant_photos` (см. ниже), джойн по `(event_id,
start_number)`.

## Схема JSON-файла

Один файл на инстанс `load_race_results.py --continuous` (то есть на конкретный
`event_id`, как и сейчас), но включает сразу обе дистанции Жары одного года — режиссёру
не нужно переключаться между несколькими URL. Если 5 км и 21.1 км Жары в конкретном
году имеют РАЗНЫЕ `event_id` (что и есть на практике — отдельные заезды), скрипт
запускается дважды (по одному инстансу `--continuous` на дистанцию, как уже происходит
сейчас), и каждый пишет **свой** файл; финальные пути — вопрос конфигурации при
реализации (например, суффикс по дистанции в имени файла).

```json
{
  "event_name": "Жара",
  "event_year": 2026,
  "distance": "21.1 км",
  "generated_at": "2026-08-23T09:14:07+07:00",
  "checkpoints": [
    {
      "code": "kt1",
      "label": "КТ1 (6.0 км)",
      "top10_absolute": [ /* до 10 объектов-строк, см. ниже */ ],
      "top10_male": [ /* до 10 */ ],
      "top10_female": [ /* до 10 */ ]
    },
    { "code": "kt2", "label": "КТ2 (6.5 км)", "...": "..." },
    { "code": "finish", "label": "Финиш", "...": "..." }
  ]
}
```

Каждая строка внутри `top10_*` — единая плоская форма, переиспользуется во всех трёх
списках (участник, попавший и в топ-10 абсолюта, и в топ-10 своего пола, несёт оба
ранга и оба отставания сразу — не нужно сопоставлять записи между списками):

```json
{
  "start_number": 245,
  "surname": "Иванов",
  "name": "Пётр",
  "sex": "M",
  "city": "Красноярск",
  "rank_absolute": 3,
  "rank_sex": 2,
  "time": "00:14:32",
  "pace": "5:49",
  "gap_absolute": "+00:18",
  "gap_sex": "Лидер",
  "photo_url": "https://analytics.krasmarafon.ru/static/images/krasmarafon/participant-placeholder.jpg"
}
```

- `sex`: `"M"` / `"F"` (маппится из `results.sex` = `"Мужчина"`/`"Женщина"`)
- Если на отметке прошло меньше 10 человек (или меньше 10 одного пола) — короче массив,
  БЕЗ пустых заглушек-объектов. Пустой список — валидное состояние (например, gender
  ещё никто не прошёл эту отметку).
- `photo_url` — **никогда `null`**. Для участников без персональной фотографии —
  ссылка на общую заглушку: `https://analytics.krasmarafon.ru/static/images/krasmarafon/participant-placeholder.png`
  (путь фиксирован; сам файл по этому пути на момент реализации — временная
  однотонная заглушка, пользователь заменит её реальной картинкой позже, путь при
  этом не меняется). Только у элитного кластера 21.1 км (~20 человек) будет
  персональное фото.

## Управление фото (админка)

Новая таблица:
```sql
CREATE TABLE participant_photos (
  id INT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  event_id INT UNSIGNED NOT NULL,
  start_number INT UNSIGNED NOT NULL,
  photo_url VARCHAR(500) NOT NULL,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uq_participant_photo (event_id, start_number)
);
```

Небольшая форма в `/admin` (в существующей вкладке — «Стартовый список» или
«Результаты», выбор при реализации): ввод номера участника → показ ФИ для сверки →
вставка ссылки → сохранение. Заполняется организатором вручную один раз до гонки по
данным анкеты элитного кластера (внешняя гугл-форма — синхронизация с ней НЕ входит в
объём этой задачи, только конечный результат — ссылка, вручную перенесённая в нашу
систему).

## Генерация и запись файла

Новый модуль `src/krasmarafon/services/live_top10_export.py`:
```python
def generate_top10_json(connection, event_id: int, output_path: str) -> None:
    ...
```
- Собирает данные по всем отметкам дистанции события `event_id` (используя уже
  загруженный `checkpoint_distances` того же события).
- **Атомарная запись**: пишет полный JSON во временный файл (`output_path + '.tmp'`),
  затем `os.replace(tmp, output_path)` — читающая сторона (nginx/инструмент режиссёра)
  никогда не видит частично записанный файл, только полностью старую или полностью
  новую версию.

Хук в `load_race_results.py::continuous_mode()` — после существующего вызова
`self._recalculate_ranks()` (когда `updated_r > 0`), добавляется вызов
`generate_top10_json(...)`, но **только если передан новый CLI-флаг**
`--broadcast-json <путь>` (opt-in — не создаём файлы для событий, которым это не
нужно). Обновление файла синхронно с интервалом опроса Copernico — какой бы `--interval`
ни был настроен для конкретного запуска, ту же частоту получает и JSON.

**Изоляция ошибок**: если `generate_top10_json()` упадёт (ошибка БД, неожиданные
данные) — исключение ловится, логируется, цикл `continuous_mode()` продолжает работу
как обычно (тот же принцип, что уже применён в проекте — единичный сбой одной
подсистемы не должен ронять весь live-пересчёт, см. известный урок с переполнением
`avg_speed_kmh` на Siberman). Файл на диске в этом случае просто не обновится в
текущем цикле — следующий цикл через несколько секунд попробует снова.

## Доставка

Новый nginx `location` (например `/live/`) → отдельная директория на VPS **вне**
`/opt/km_track/static/` (у которой уже настроен `Cache-Control: public,
max-age=604800` — 7 дней, что убьёт весь смысл реального времени). Явно
`add_header Cache-Control "no-store";`. Публичный URL, без авторизации — по прецеденту
других публичных JSON-эндпоинтов проекта (`/api/event-results` и т.п.).

## Тестирование

- Юнит-тесты `generate_top10_json()` (замоканная БД):
  - нарезка топ-10/меньше (когда прошло < 10 человек)
  - раздельные списки абсолют/муж/жен, единая форма строки с обоими рангами
  - форматирование отставания (`+ММ:СС`, `+ЧЧ:ММ:СС` при ≥ часа, `"Лидер"` у первого)
  - `photo_url` — реальная ссылка из `participant_photos`, либо заглушка, если записи
    нет
  - атомарность записи (файл-результат либо отсутствует, либо полностью валиден)
- Ручная проверка на реальном `event_id` в dev-окружении: сверка чисел с уже работающей
  `/results`, проверка заголовков кэша через `curl -I` на проде после деплоя.

## Явно вне объёма

- Автоматическая синхронизация с внешней гугл-анкетой элитного кластера — фото
  переносятся вручную через админку.
- Дистанция «2 км» — нет промежуточных КТ, топ-10 по отметкам не строится.
- Официальное (gun-time) время/место на отметках — не существует в БД на уровне КТ,
  не реализуется.
