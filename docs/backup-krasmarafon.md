# Бэкап и автономная выдача стартовых пакетов

Цикл каждые 8 часов сохраняет MySQL и штатные выгрузки Tilda CRM. Затем строит отдельный XLSX по каждому настроенному старту. Оба источника сохраняются заранее, пока доступны. Выдача использует локальный файл и отдельный журнал. Цель по давности данных — 24 часа.

## Подготовка пилота

1. Выбрать постоянно включённый Windows-компьютер вне Reg.ru, второй зашифрованный носитель и устройства выдачи. Включить шифрование и ограничить доступ к каталогам, включая временные файлы и профиль браузера. Доступ к ключам, секретам и процедуре восстановления должен быть у назначенных сотрудников. Архивы и рабочие файлы не размещать в Git или общем облачном каталоге.
2. Установить Python 3.11 или новее, MySQL Client того же семейства, что и production, и библиотеки для XLSX и браузера. Скопировать [пример конфигурации](backup-krasmarafon.example.json) в защищённый каталог вне репозитория. Заменить все значения в угловых скобках.

   ```powershell
   python -m pip install openpyxl playwright
   python -m playwright install chromium
   ```

3. Проверить движки, версию, размеры и нагрузку MySQL. Согласовать отдельную учётную запись с правами чтения схемы и просмотра объектов, необходимых для дампа, без записи. Получить UUID каждого сервера запросом `SELECT @@server_uuid` в рамках настройки. Для source использовать отдельно обслуживаемый SSH-туннель на loopback или прямой TLS с проверкой имени и доверенным CA (`tls_mode: VERIFY_IDENTITY`, `tls_ca`). Для каждого клиента создать отдельный UTF-8 файл опций с секцией `[client]` и единственной опцией `password`. Исключить миграции схемы из окна дампа.
4. Сверить CRM-листы, стадии и заголовки на одном актуальном старте. Пример рассчитан на отдельный экспорт CRM для старта. Если экспорт общий, добавить сопоставление `event_name` и `event_year` либо колонку `products` с распознаваемым названием продукта. Включить все стадии с оплатами, отменами и возвратами. Для нескольких экспортов перечислить их в `crm_exports`. В `crm_columns` можно добавить `order_id`, `distance` и `kit`, когда фактический файл содержит эти колонки. Сверить настройки допустимых статусов и совпадения идентификаторов с организатором.
5. Запустить один раз от пользователя, под которым будет работать планировщик. Войти в Tilda под учётной записью с доступом к нужным CRM-листам. При истечении сессии повторить команду. Файл сессии даёт доступ к CRM и должен храниться отдельно от выгрузок.

   ```powershell
   $kmConfig = 'D:\KM-Backup\private\config.json'
   python scripts/backup_tilda.py login --config $kmConfig
   python scripts/backup_tilda.py capture --config $kmConfig
   python scripts/backup_mysql.py capture --config $kmConfig
   python scripts/backup_krasmarafon.py cycle --config $kmConfig
   ```

## Расписание и выдача

- Зарегистрировать Windows-задачи скриптом ниже после ручного пилота. Время соответствует часовому поясу компьютера. Нужны доступ к дискам и сеть из фонового сеанса. Для постоянного канала уведомлений задать `KM_BACKUP_ALERT_URL` и `KM_BACKUP_ALERT_TOKEN` в окружении пользователя планировщика. Канал принимает HTTPS POST с bearer-токеном. Уведомления содержат только имя источника и возраст копии. Логи находятся в каталоге архивов.

  ```powershell
  .\scripts\register_krasmarafon_backup.ps1 -Python (Get-Command python).Source -Config $kmConfig -Credential (Get-Credential)
  ```

- После назначения номеров и перед выдачей запустить `cycle`. Проверить время источников и лист «Проверить». Закрыть предыдущий XLSX перед обновлением. Если компьютер выдачи отдельный, доставить свежие файлы на зашифрованном носителе и убедиться, что их можно открыть с локального диска. Команда `publish` повторно копирует готовый список на настроенные пути, сохраняя существующие журналы. Перед отъездом отключить сеть и повторить открытие списка.
- Во время сбоя открыть `STARTLIST-*.xlsx` и вести отдельный `JOURNAL-*.xlsx`. За каждым рабочим местом закрепить диапазон участников. Спорные записи передавать старшему. После восстановления свести журналы по идентификатору заявки перед продолжением обычной выдачи.

## Восстановление и приёмка

- Для резервной копии уже работающей локальной базы предусмотрена отдельная команда `python scripts/backup_mysql.py capture-local --config <путь-к-dev-backup.json>`. Вне Git задайте `storage` и раздел `local_backup` с абсолютными путями `env_file` (существующий `.env.local`), `client`, `dump` и UUID локального экземпляра в `server_uuid`. Команда читает только `127.0.0.1:3308/krasmarafon`, кладёт проверенные копии в `<storage>/mysql-dev` и ведёт там `local-backup.log`. Это сохранение текущего состояния dev. Для обновления dev с production используйте снимок основного контура.
- Еженедельная задача архивирует снимок для разработки. Чтобы обновить dev, подготовить пустой локальный MySQL с отключённым планировщиком событий и отдельным UUID. Запустить `python scripts/backup_krasmarafon.py dev --config $kmConfig --restore`, сверить результат и переключить dev на проверенный экземпляр. Сохранить предыдущий экземпляр до переключения. Каждый следующий импорт выполняется в свежий пустой слот.
- Для аварийной репетиции выбрать архив MySQL и отдельный пустой экземпляр вне Reg.ru, указанный в `mysql.recovery`. Запустить `python scripts/backup_mysql.py recover --config $kmConfig --bundle <каталог-дампа> --restore`. Сверить объекты схемы и контрольные количества, открыть CRM-архив и сравнить сформированный список по пилотному старту с рабочим. Зафиксировать время восстановления. Порядок запуска полного сервиса хранить вместе с перечнем требуемых настроек, файлов и секретов.
- Проверить повреждённый файл, сбой одного источника и истёкший вход CRM. Проверить пороги уведомлений 16 и 24 часа, журнал выдачи после замены XLSX и сценарий одновременной недоступности Tilda и Reg.ru. Завершить пилот после подтверждения организатором. Только затем добавить остальные старты.
